# 롤업 개발 키트

`x/rdk` 모듈은 개발자가 QoreChain 위에 애플리케이션별 롤업을 배포할 수 있도록 하는 포괄적인 롤업 개발 키트(RDK)를 제공합니다. 네 가지 정산 패러다임, 다중 시퀀서 모드, 플러그형 데이터 가용성 백엔드, 그리고 AI 보조 구성 최적화를 지원합니다.

:::caution 초기 단계 기능
이 모듈은 메인넷(체인 버전 높이 3,742,566까지 **v3.2.3**, 그 블록부터 **v3.2.4**)과 테스트넷(**v3.2.4**)에 배포되어 있지만, **어느 네트워크에서도 아직 롤업이 생성된 적이 없습니다**(2026년 10월 21일 확인: 두 네트워크 모두에서 `GET /qorechain/rdk/v1/rollups`가 빈 목록을 반환합니다). 아래에 설명된 여러 기능은 현재 처음부터 끝까지 사용할 수 없으며, 각 기능을 설명하는 곳에 상태를 명시합니다. 개발자용 사용 안내는 [롤업 개요](/rollups/overview)를 참조하십시오.
:::

---

## 정산 패러다임

QoreChain RDK는 **optimistic**, **zk**, **based**, **sovereign**의 네 가지 서로 다른 정산 모드를 지원하며, 각각 신뢰 가정, 최종성 특성, 증명 요구사항이 다릅니다.

### Optimistic 정산 {#optimistic-settlement}

Optimistic 롤업은 트랜잭션이 기본적으로 유효하다고 가정하고 분쟁 해결을 위해 사기 증명(fraud proof)에 의존합니다.

* **증명 시스템**: 대화형 사기 증명
* **이의 제기 기간(Challenge window)**: 604,800초(기본값, 7일). **v3.2.4 이전(높이 3,742,566 이전의 메인넷 v3.2.3):** 체인은 이를 블록당 고정 6초로 블록 수로 변환하여 **100,800 블록**이 되므로, 실제 경과 시간은 실제 블록 시간에 따라 달라집니다(메인넷의 현재 ≈3.2초 블록에서는 약 3.7일). 일 단위가 아닌 블록 단위로 계획하십시오. **v3.2.4부터:** 업그레이드 높이부터 제출된 배치의 경우 기간이 블록 시간의 초 단위로 측정됩니다(온전한 7일). 그 이전에 제출된 배치는 블록 수 규칙을 유지합니다. 테스트넷은 2026년 10월 19일 높이 8,337,253에서 v3.2.4를 적용했으며, 메인넷은 높이 3,742,566에서 적용합니다(거버넌스 제안 13).
* **이의 제기 보증금(Challenge bond)**: 1,000 QOR(1,000,000,000 uqor) — 사기 증명 이의 제기를 제출하는 데 필요(`nft` 및 `custom` 사전 설정; `defi`, `gaming`, `enterprise` 사전 설정은 이의 제기 기간이 없으므로 보증금을 설정하지 않음)
* **최종성**: 이의 제기 기간이 유효한 이의 제기 없이 만료될 때까지 지연됨
* **자동 최종화**: `EndBlocker`는 이의 제기 기간이 분쟁 없이 경과하면 배치를 자동으로 최종화합니다. 이의가 제기된 배치는 자동으로 최종화되지 않습니다. 롤업 생성자가 먼저 이의 제기를 해결해야 합니다([롤업 배포하기](/rollups/deploying-a-rollup#challenge-a-batch-optimistic-rollups) 참조).

**배치 수명 주기**:

```
Submitted → [challenge window expires] → Finalized
Submitted → [fraud proof submitted] → Challenged → Rejected
```

### ZK(영지식) 정산 {#zk-zero-knowledge-settlement}

ZK 롤업은 상태 전이의 정확성을 보장하는 암호학적 유효성 증명을 제공합니다.

* **증명 시스템**: SNARK(BLS12-381 상의 Groth16) 또는 STARK(투명, 신뢰 설정 불필요)
* **최종성**: 증명 검증 시 즉시 — 이의 제기 기간 불필요
* **최대 증명 크기**: 1 MB(1,048,576 바이트)
* **재귀 깊이(Recursion depth)**: 구성 가능한 증명 집계 깊이(기본값: 1)
* **성숙도**: SNARK 배치는 롤업과 함께 저장된 검증 키에 대해 온체인에서 검증됩니다(BLS12-381 상의 Groth16). `create-rollup`으로 생성된 롤업에는 현재 검증 키가 없으므로, ZK 배치는 아직 처음부터 끝까지 최종화될 수 없습니다. STARK 검증은 실험적입니다: 옵트인 방식이며 롤업 자체의 상태 전이가 아니라 시연용 회로를 검사합니다. ZK 정산은 프로덕션 준비가 되지 않은 것으로 간주하십시오.

**배치 수명 주기**:

```
Submitted + valid proof → Finalized (instant)
```

### Based 정산

Based 롤업은 트랜잭션 시퀀싱을 L1(QoreChain) 프로포저에게 위임하여 호스트 체인의 활성성(liveness) 및 검열 저항성 보장을 상속받습니다.

* **증명 시스템**: 불필요 — L1 프로포저가 신뢰의 원천
* **시퀀서**: `based` 시퀀서 모드를 사용해야 함(검증에 의해 강제)
* **최종성**: QoreChain에서 2블록 확인
* **포함 지연(Inclusion delay)**: 롤업 트랜잭션의 강제 포함 전 구성 가능한 블록 수
* **우선순위 수수료 공유**: L1 프로포저에게 지급되는 우선순위 수수료의 구성 가능한 비율

**배치 수명 주기**:

```
Submitted → [2 L1 blocks] → Finalized (auto)
```

### Sovereign 정산

Sovereign 롤업은 독립적인 합의로 작동하며 자체적으로 트랜잭션을 시퀀싱합니다. 검증 가능성을 위해 상태를 QoreChain에 앵커링하지만 최종성을 위해 호스트 체인에 의존하지는 않습니다.

* **증명 시스템**: 없음
* **최종성**: 독립적 — 롤업 자체 합의에 의해 결정됨
* **상태 앵커링**: 상태 루트가 투명성과 검증 가능성을 위해 QoreChain에 게시되지만 강제되지는 않음
* **자동 최종화**: 없음 — sovereign 롤업은 자체적으로 최종성을 관리

| --------------- | -----------: | --------: | --------: | -------: |

## 사전 설정 프로파일

RDK는 일반적인 사용 사례에 최적화된 턴키 롤업 구성을 제공하는 **5가지 사전 설정 프로파일**을 함께 제공합니다. 각 사전 설정은 대상 도메인에 맞게 조정된 정산 패러다임, 시퀀서 모드, 데이터 가용성 백엔드, 가스 모델, VM을 번들로 제공합니다:

| 프로파일          | 정산(증명)               | 시퀀서     | DA              | 가스 모델     | VM      | 대상 사용 사례 |
| ---------------- | ------------------------ | --------- | --------------- | ------------ | ------- | --------------- |
| **`defi`**       | zk (SNARK)               | dedicated | native          | EIP-1559     | EVM     | 트레이딩, 대출, AMM 스타일 애플리케이션 |
| **`gaming`**     | based                    | based     | native          | flat         | custom  | 고처리량, 저지연 게임 상태 및 게임 내 경제 |
| **`nft`**        | optimistic (fraud)       | dedicated | native (Celestia DA 예정) | standard | QoreChain Native | NFT 발행, 마켓플레이스, 디지털 수집품 |
| **`enterprise`** | based                    | based     | native          | subsidized   | EVM     | 수수료가 후원되는 허가형 및 컨소시엄 배포 |
| **`custom`**     | 완전 매개변수화           | 완전 매개변수화 | 완전 매개변수화 | 완전 매개변수화 | 완전 매개변수화 | 모든 필드를 사용자가 정의 |

`custom` 프로파일은 모든 필드를 사용자가 설정하도록 남겨둡니다. 각 사전 설정에 번들된 정확한 값은 RDK가 성숙함에 따라 변경될 수 있습니다. 권위 있는 사전 설정별 매개변수를 확인하려면 `qorechaind query rdk config`(또는 `@qorechain/rdk`의 `RdkClient.params()`)로 라이브 구성을 쿼리하세요. 그리고 `based` 정산은 항상 `based` 시퀀서 모드와 짝을 이룬다는 점에 유의하세요.

## 시퀀서 모드

시퀀서는 롤업 블록 내에서 트랜잭션을 정렬하는 주체를 결정합니다.

:::note 현재 강제되는 사항
온체인에서 배치는 롤업에 구성된 시퀀서 주소만 제출할 수 있으며, 구성된 주소가 없는 경우(모든 사전 설정이 해당) 생성자가 제출할 수 있습니다. `shared` 및 `based` 모드는 롤업 구성에 기록되지만, QoreChain은 아직 공유 시퀀서 명단이나 L1 프로포저를 배치 제출자로 허용하지 않습니다. 이러한 모드는 의도된 설계를 설명합니다.
:::

### Dedicated 시퀀서

단일 운영자가 모든 롤업 트랜잭션을 시퀀싱합니다.

* **운영자**: 단일 지정 주소
* **지연 시간**: 가능한 가장 낮음 — 단일 당사자 정렬
* **신뢰**: 활성성 및 공정한 정렬을 위해 시퀀서 운영자에 대한 신뢰가 필요

### Shared 시퀀서

시퀀서 집합이 공동으로 트랜잭션을 정렬합니다.

* **상태**: 현재는 레이블일 뿐 — 명단이 아직 온체인에서 허용되지 않음(위의 참고 사항 참조)
* **최소 집합 크기**: 구성 가능(기본값: 1)
* **지연 시간**: 다자간 조정으로 인해 약간 더 높음
* **신뢰**: 시퀀서 집합 전반에 분산됨

### Based 시퀀서

QoreChain L1 프로포저가 롤업 트랜잭션을 시퀀싱합니다.

* **상태**: 현재는 레이블일 뿐 — L1 프로포저가 아직 배치 제출자로 허용되지 않음(위의 참고 사항 참조)
* **포함 지연(Inclusion delay)**: 강제 포함 전 구성 가능한 블록 수(기본값: 10)
* **우선순위 수수료 공유**: L1 프로포저에게 지급되는 우선순위 수수료의 구성 가능한 비율
* **신뢰**: QoreChain의 검증자 집합 보안 및 검열 저항성을 상속
* **요구사항**: Based 정산 모드는 based 시퀀서를 필요로 함(검증 시 강제)

## 데이터 가용성 백엔드

### Native DA

QoreChain 자체 내의 온체인 KV 저장소 블롭 스토리지입니다.

:::caution 블롭을 게시할 공개된 방법이 아직 없음
이 모듈은 블롭 스토리지, 보존, 가지치기를 정의하지만, 현재 릴리스에는 블롭을 게시하기 위한 트랜잭션 메시지가 없습니다. `native` 또는 `both` 롤업에서 데이터 해시를 지정하는 배치는 일치하는 블롭을 저장할 수 없으므로 거부됩니다. [데이터 가용성](/rollups/data-availability)을 참조하십시오.
:::

| 매개변수             | 값                                                                                                 |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **최대 블롭 크기**    | 2 MB(2,097,152 바이트)                                                                              |
| **보존 기간**         | 432,000 블록(메인넷의 현재 ≈3.2초 블록에서 약 16일. 이 수치는 블록 시간에 따라 변동)                  |
| **자동 가지치기**     | 만료된 블롭은 `EndBlocker`에서 가지치기됨 — 데이터는 제거되지만 커밋먼트 메타데이터는 보존됨           |
| **커밋먼트**          | 블롭 데이터의 SHAKE-256(32바이트) 해시                                                              |

### Celestia DA

Celestia의 전용 DA 레이어를 사용하는 IBC 기반 데이터 가용성입니다.

* **상태**: 현재 릴리스에서 스텁 처리됨 — 단독 백엔드로 선택되면 오류 반환
* **네임스페이스 지원**: 롤업별 네임스페이스가 블롭 스키마에서 지원됨
* **예정**: Celestia의 블롭 제출 및 검증과의 완전한 IBC 통합

### Both(중복)

Native 및 Celestia 백엔드 모두에 블롭을 동시에 저장합니다.

* 현재 릴리스에서는 native 블롭만 실제로 저장되며, Celestia 구성 요소에 대해서는 경고가 로깅됩니다.

## 롤업 수명 주기

```
Pending → Active → Paused → Active → Stopped
                      ↑                  |
                      └──────────────────┘
                      (can resume from paused,
                       stopped is permanent)
```

| 상태        | 설명                                                          |
| ----------- | ------------------------------------------------------------ |
| **Pending** | 롤업이 등록되었지만 아직 활성화되지 않음                        |
| **Active**  | 롤업이 라이브 상태이며 배치를 처리 중                          |
| **Paused**  | 생성자에 의해 일시적으로 중단됨(재개 가능)                     |
| **Stopped** | 영구적으로 폐기됨 — 생성자의 에스크로에 남은 금액이 반환됨([에스크로 원장](#escrow-ledger) 참조) |

생성 시, 롤업 상태는 스테이크 에스크로와 생성 소각이 성공한 직후 `Active`로 설정됩니다(레이어 등록은 시도되지만 치명적이지 않음). 롤업을 일시 중지, 재개 또는 중지할 수 있는 것은 생성자뿐입니다(체인 버전 v3.2.0부터 강제).

## 배치 수명 주기

정산 배치는 롤업 상태 루트의 상태 진행을 추적합니다:

```
Submitted → Finalized                              (happy path)
Submitted → Challenged → Rejected                  (fraud detected)
```

| 상태           | 설명                                              |
| -------------- | ------------------------------------------------- |
| **Submitted**  | 배치가 QoreChain에 게시되어 최종화 대기 중          |
| **Challenged** | 사기 증명 이의 제기 제출됨(optimistic 전용)         |
| **Finalized**  | 배치가 정규(canonical)로 수락됨                     |
| **Rejected**   | 성공적인 이의 제기에 의해 배치가 무효화됨            |

### 자동 최종화 규칙

| 정산 모드        | 최종화 트리거                                               |
| --------------- | ----------------------------------------------------------- |
| **Optimistic**  | 제출 후 100,800 블록(기본 기간) 동안 이의 제기 없음. v3.2.4 이후 제출된 배치(테스트넷은 높이 8,337,253부터, 메인넷은 높이 3,742,566부터)에 대해서는 블록 시간 기준 604,800초 |
| **ZK**          | 유효한 증명 제출 시 즉시                                      |
| **Based**       | 제출 후 2 L1 블록                                            |
| **Sovereign**   | 없음 — 롤업 자체 합의에 의해 관리됨                           |

자동 최종화는 optimistic 및 based 롤업의 경우 `EndBlocker`에서 실행됩니다. ZK 배치는 배치 제출 중 인라인으로 최종화됩니다.

## Multilayer 통합

RDK 모듈은 교차 레이어 상태 관리를 위해 `x/multilayer`와 통합됩니다:

### 레이어 등록 {#layer-registration}

롤업이 생성되면 모듈은 `RegisterSidechain`을 통해 해당 롤업의 레이어를 등록하므로, 온체인에서 레이어 유형은 **`sidechain`**이고, `proposed` 상태로 시작하며, multilayer 사이드체인 한도(`max_sidechains`, 기본값 **10**)에 포함되고, 생성자의 `min_sidechain_stake`(1,000 QOR)를 잠급니다. 등록에는 다음이 포함됩니다:

* 레이어 ID(롤업 ID와 일치)
* 목표 블록 시간 및 블록당 최대 트랜잭션 수
* 지원되는 VM 유형 및 도메인
* 정산 간격

등록은 **비치명적(non-fatal)**입니다: 등록이 실패해도(잔액 부족 또는 한도 도달) 롤업은 여전히 생성되지만, 레이어가 없어 앵커링할 수 없습니다. 정산 앵커는 레이어가 `active`일 것을 요구하지 않습니다. RDK 롤업이 등록하는 레이어는 `proposed` 상태로 유지되며 생성자가 여전히 앵커링할 수 있습니다([앵커 제출](/architecture/multilayer-architecture#anchor-submission) 참조).

### 상태 앵커링 {#state-anchoring}

정산 배치는 `x/multilayer`에 앵커링될 수 있으며, 이는 롤업 생성자의 포스트 양자 서명 하에 레이어 ID, 레이어 높이(배치 인덱스), 상태 루트, 검증자 집합 해시, 트랜잭션 수를 기록합니다.

* **v3.2.2부터(메인넷과 테스트넷에서 라이브):** `MsgSubmitBatch`에는 두 개의 선택적 필드가 있습니다. `anchor_signature`는 배치의 **v2 앵커 서명 바이트**에 대한 생성자의 ML-DSA-87 서명이며([앵커 읽기](/architecture/multilayer-architecture#reading-anchors) 참조), 이것이 있으면 배치가 **같은 트랜잭션**에서 `x/multilayer`에 앵커링되고, 앵커가 거부되면 배치도 거부됩니다. `validator_set_hash`는 앵커에 담기고 서명으로 보호되는 롤업의 검증자 집합 커밋먼트입니다. CLI에서는 `qorechaind query rdk anchor-sign-bytes <layer-id> <batch-index> <state-root-hex> --chain-id <id> --tx-count <n>`이 서명할 바이트를 출력하고(`<layer-id>`는 롤업의 레이어 ID이며, RDK를 통해 생성된 롤업에서는 롤업 ID와 같습니다), `tx rdk submit-batch ... --anchor-signature <hex> --validator-set-hash <hex>`가 이를 제출합니다.
* **서명이 없으면** 배치는 이전과 똑같이 앵커링 없이 정산됩니다. 이 필드를 보내지 않는 클라이언트는 앵커링되지 않은 배치를 생성하므로, 사용하는 툴킷이 이를 지원하는지 확인하세요. TypeScript `@qorechain/rdk` 0.6.0은 클라이언트가 하이브리드로 서명하고 롤업의 생성자일 때 앵커에 서명하며(그렇지 않으면 앵커링 없이 제출합니다), Python, Go, Rust, Java 클라이언트는 이 필드를 구성하지 않습니다. 어느 네트워크에도 롤업, 레이어, 앵커가 아직 없으므로 기록된 앵커가 없으며 이 경로는 실제 네트워크에서 아직 검증되지 않았습니다.

앵커가 증명하는 것과 증명하지 않는 것은 [정산 영수증](/rollups/settlement-receipts)을 참조하십시오.

## 에스크로 원장 및 출금 {#escrow-ledger}

모든 롤업의 에스크로는 하나의 통합된 모듈 잔액에 있습니다. **v3.2.3**(메인넷 높이 3,662,051, 2026년 10월 20일)부터 롤업별 **에스크로 원장**이 해당 풀에서 각 롤업이 보유한 금액의 단일 기록입니다:

* `create-rollup`은 롤업이 실제로 보유하는 에스크로, 즉 스테이크에서 1% 생성 소각분을 뺀 금액을 원장에 기록합니다.
* 출금(`tx rdk execute-withdrawal`)과 사기 증명 보상은 원장에서 지급되고 원장에서 차감됩니다. 롤업이 아직 보유한 금액보다 큰 출금은 에스크로 부족 오류로 거부됩니다.
* `stop-rollup`은 원장에 남은 금액만 환불하고 원장을 0으로 만듭니다. 중지된 롤업은 더 이상 출금을 지급하지 않습니다.
* 롤업 쿼리가 반환하는 읽기 전용 `RollupView`에는 `escrow_balance`, 즉 해당 롤업을 위해 아직 보유 중인 uqor가 포함됩니다.

v3.2.3 이전에는 원장에 0이 기록되었으므로 모든 출금이 안전하게 실패했습니다(fail closed). 따라서 `execute-withdrawal`은 메인넷에서 v3.2.3부터만 성공할 수 있습니다. 클라이언트가 수수료를 내기 전에 실행해야 할 확인 사항: denom은 정확히 `uqor`여야 하고, 금액은 양수여야 하며, 머클 증명은 최대 64단계이고 모든 형제 노드가 정확히 32바이트여야 하고, 제출자와 수신자는 유효한 `qor1…` 주소여야 합니다. 출금에는 또한 `withdrawals_root`를 커밋한 최종화된 배치가 필요하며, 각 출금 리프는 한 번만 지급될 수 있습니다.

## RDK 상태 읽기 {#reading-state}

RDK 쿼리는 메인넷과 테스트넷에서 `/qorechain/rdk/v1/` 아래 REST로 제공됩니다:

| 경로 | 반환 내용 |
| --- | --- |
| `/params` | 모듈 매개변수(위의 표) |
| `/rollups` 및 `/rollup/{rollup_id}` | `escrow_balance`를 포함한 롤업 레코드 |
| `/batches/{rollup_id}` | 페이지로 나뉜 배치(`start_index`, `limit` 기본값 50 최대 100, `next_index`) |
| `/batch/{rollup_id}/{batch_index}` 및 `/latest_batch/{rollup_id}` | 배치 하나 또는 가장 최근 배치 |
| `/blob/{rollup_id}/{blob_index}` | `expires_at_height`를 포함한 블롭 메타데이터(블롭 바이트는 반환되지 않음) |

`qorechaind query rdk config`는 모듈 매개변수를 출력합니다(경로는 `/params`이며 `/config` 경로는 없습니다). 롤업 및 레이어 ID는 v3.2.2부터 강제되는 [레이어 및 롤업 ID](/architecture/multilayer-architecture#id-grammar)의 ID 문법과 일치해야 합니다.

## Burn 통합

롤업 생성 시, **스테이크 금액의 1%**가 `rollup_create` 소각 채널을 통해 `x/burn` 모듈로 소각됩니다. 예를 들어, 최소 10,000 QOR 스테이크로 롤업을 생성하면 100 QOR가 영구적으로 소각됩니다. 나머지 9,900 QOR는 에스크로에 보관되며 롤업이 중지될 때 그중 남은 금액이 생성자에게 반환됩니다(에스크로에서 지급된 출금과 사기 증명 보상은 환불액을 줄입니다). 생성 소각은 체인 버전 v3.2.0부터 강제되며, 이전 릴리스에서는 적용되지 않았습니다.
