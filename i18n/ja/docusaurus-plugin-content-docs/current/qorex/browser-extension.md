# QoreX ブラウザ拡張機能

QoreX の**ブラウザ拡張機能**は、デスクトップ版の QoreChain ウォレットです。これは**単独で完結するウォレット**であり、ウォレットの作成やインポート、QOR の保有と送信、dApp への接続が行えます。さらに、あらゆる Web サイトが QoreX を検出し、すべてのリクエストを明示的かつ内容の解読された承認へと変えるための要となる部分でもあります。

3 つのストアで**公開済み・提供中**です。

## インストール {#install}

| ブラウザ | インストール |
|---|---|
| **Chrome および Chromium 系ブラウザ**（Brave、Edge、Arc、Opera） | https://chromewebstore.google.com/detail/qorex/cflpnggbnnifibblifgbeobogdpfjpcg |
| **Firefox** | https://addons.mozilla.org/firefox/addon/qorex/ |
| **Safari（macOS 10.14 以降）** | https://apps.apple.com/us/app/qorex-wallet/id6794132220 |

### どのバージョンがどこで提供されているか {#versions}

ストアの審査が完了する時期は同じではないため、現在公開されているバージョンはブラウザごとに異なります。

| ブラウザ | 公開バージョン |
|---|---|
| **Firefox** | **0.1.8**（0.1.9 は申請済み、審査中） |
| **Chrome / Chromium** | **0.1.5**（0.1.9 は申請済み、審査中） |
| **Safari（macOS）** | **QoreX Wallet** の macOS アプリに同梱されており、アプリ自身の `1.x` 系のバージョン番号を使用します。Mac App Store で現在配信されているのは **1.1**（拡張機能 0.1.5 を含む）で、**1.2**（0.1.9 を含む）は申請済み・審査中です |

ここに書かれている機能でも、お使いのブラウザにはまだ届いていない場合があります。何かが利用できると思い込む前に、上の表を確認してください。

**0.1.5** では、[Solana Wallet Standard による検出](#standards)、[パスキーによるロック解除](#security)、完全に実装された [SVM dApp レーン](#standards)、および [Dashboard 接続ブリッジ](#dashboard-bridge)が追加されています。（バージョン 0.1.4 は公開されませんでした。その変更点は 0.1.5 でユーザーに届きます。）

**0.1.6〜0.1.9** では、順に次の変更が追加されました。ベスティング（権利確定）を考慮し、拒否理由を正直に示す送金メッセージ、ポップアップのホーム画面に直接表示されるアカウントアドレスとリアルタイム残高、そして **0.1.9** では、送金画面から直接 [@handle 宛に支払う](#handle-send)機能、[アドレスの QR コードを表示する受け取り画面](#receive)、[言語選択](#language)（モバイルアプリと同じ 10 言語に対応)、そして[ベスティング残高](#vesting)からわかりにくい「次回のロック解除日」表示を削除したことです。

**パーミッションの範囲は 0.1.3 以降変わっていません** — [QoreX が要求するパーミッション](#permissions)を参照してください。

:::note
Safari では、承認画面はポップアップウィンドウではなくブラウザのタブで開きます。この拡張機能は、同一のコードベースから Apple の Safari web-extension ラッパーでパッケージ化されています。
:::

## ウォレットの作成または復元 {#wallet}

ポップアップを開き、次のいずれかを選択します。

- **ウォレットを作成** — お使いのデバイス上で新しい 24 語のリカバリーフレーズ（256 ビットのエントロピー）を生成し、QoreChain のアイデンティティを導出して、パスワード（および任意でパスキー。[セキュリティ](#security)を参照）で保護された保管領域に封入します。
- **ウォレットをインポート** — 既存の 24 語のフレーズから復元します。

拡張機能は自前の鍵を保持しており、モバイルアプリを必要としません。ニーモニックはポップアップからエクスポートすることもできます。鍵がデバイスの外に出ることはありません。

:::note ブラウザプロファイルごとに 1 アカウント
モバイルアプリは 1 つのリカバリーフレーズから複数の QoreChain アカウントを保持できますが、拡張機能が管理するアカウントは常に**1 つ**だけです。ステーキング、ポートフォリオ、Q-Day Scanner、ソーシャルリカバリー、Legacy Protocol、支払いリクエスト、デバイスの紐付けはモバイル限定の機能です — 全体の比較は [QoreX Wallet](/qorex/overview#platform-availability) を参照してください。
:::

## アカウント、残高、@handle {#account}

ポップアップの待機画面には、あなたの `qor1…` アドレス（タップでコピー可能）とリアルタイムの QOR 残高が表示されるため、どちらを確認するにもブロックエクスプローラーを開く必要はありません。

### ベスティング（ロック中）残高 {#vesting}

アカウントにベスティング中の QOR がある場合（たとえば未解放の TGE 配分など）、残高は**現在利用可能**な分と**まだロック中**の分に分かれて表示され、利用可能額を超える送金はネットワークに届く前に拒否されます。手数料を取られたうえでオンチェーンで失敗するようなことはありません。QoreX はここに「次回のロック解除日」を意図的に表示しません。ベスティングのスケジュールはガバナンスによって変更され得るため、残高カード上の日付は QoreX が保証できない約束のように見えてしまうからです。正確な状態を保てるのは、利用可能額とロック中額の内訳のほうです。

### @handle を取得する

ポップアップから、このアカウントのアドレスに対して一意の **@handle**（たとえば `@liviu`）を、モバイルアプリと同じように取得できます。この取得申請はアカウント自身の鍵で署名され、そのアドレスに紐付けられるため、モバイルアプリと Dashboard は誰かがあなた宛に送金しようとしたときにこれを解決できます。ハンドルがウォレット全体ではなくアドレスに紐付けられている仕組みについては、[@handle](/qorex/account-and-dashboard#handle) を参照してください。

## @handle 宛に送金する {#handle-send}

0.1.9 以降、アドレスを調べる代わりに、登録済みの @handle に直接支払うことができます。

1. ポップアップを開き、**送金**をタップします。
2. 宛先欄に、`qor1…` アドレスの代わりに `@` に続けてハンドル（たとえば `@liviu`）を入力します。
3. QoreX はハンドルを解決し、署名する前に**解決されたアドレス**を表示します — これが想定どおりか必ず確認してください。
4. 金額を入力して確定します。

解決結果は、署名させる前に 2 つの方法で検証されます。1 つは拡張機能に組み込まれた信頼鍵と照合するレジストリのアテステーション、もう 1 つはハンドル所有者自身によるクレームへの署名です。いずれかの検証に失敗した応答は完全に拒否されます — QoreX は未検証のアドレスを代わりに表示することはありません。あるハンドルに初めて支払うとき、QoreX はその解決先アドレスを記憶(ピン留め)します。その後同じハンドルが**別の**アドレスに解決された場合、QoreX は処理を止め、続行するかどうかを判断できるよう新旧両方のアドレスを全文表示します。

## 受け取り {#receive}

ポップアップで**受け取る**をタップすると、あなたの `qor1…` アドレスが QR コード（QoreChain のアイコンが埋め込まれています）とコピーボタンとともに表示されます。スマートフォンからスキャンするか、アドレスを直接貼り付けてください。

### 外部ネットワークでの送信 {#send-external}

Native レーン上の QOR に加えて、ポップアップは同じリカバリーフレーズから導出された外部ネットワーク上の資産も送信できます。

| 種類 | ネットワーク | 同梱されるトークン |
|---|---|---|
| EVM | Ethereum、BNB Chain、Polygon、Arbitrum、Base、OP Mainnet、Avalanche C-Chain | ERC-20 銘柄（EVM 各チェーンの USDC・USDT、Ethereum 上の DAI） |
| SVM | Solana | SPL 銘柄（USDC、USDT） |
| Cosmos | Cosmos Hub、Osmosis、Celestia | IBC 経由の Noble USDC。任意のメモ欄あり |

外部ネットワークへの送金を行う前に、次の明示的な確認事項にチェックを入れる必要があります。**「外部ネットワークは従来型の署名のみを受け付けます。お使いの QOR とは異なり、この送金は量子耐性を持ちません。」** 外部チェーンは耐量子署名を扱うことができず、QoreX はこの事実を決して隠しません。

## 対応しているウォレット規格 {#standards}

QoreX は 3 つのインターフェースをすべて `window.qorex`（`{ evm, native, svm }`）としてページ上に注入し、[`@qorechain/connect`](/sdk/overview) の検出コントラクトを通じて検出可能にしています。

| 規格 | 概要 | 開発者にとっての意味 |
|---|---|---|
| **EIP-1193** | Ethereum プロバイダの JavaScript API（`request(...)`、イベント）。 | 既存の ethers.js / viem / web3.js のコードは変更なしで QoreX の EVM レーンと通信できます。数値エラーコード（例: `4902`）はそのまま転送されます。 |
| **EIP-6963** | 複数ウォレットのプロバイダ検出（announce / request イベント）。 | QoreX は他のあらゆるウォレットと並んで自らを告知します。**`window.ethereum` を上書きすることは決してありません**。そのため、競合なくユーザーがサイトごとに QoreX を選択できます。 |
| **Keplr 方式の `signDirect`** | `window.qorex.native` 上の Cosmos `OfflineDirectSigner` 形式のプロバイダ。 | Cosmos 系の dApp は、Keplr を使う場合と同じ方法で QoreChain の **Native レーン**トランザクションに署名できます。耐量子レイヤーはあらかじめ適用済みです（[耐量子署名](#pqc)を参照）。 |
| **Solana Wallet Standard**（0.1.5 以降） | Solana dApp 向けのネイティブなウォレット検出（`wallet-standard:register-wallet` / `app-ready`）。 | Solana の dApp は**QoreX を自動検出**します — 独自の統合作業は不要です。機能: `standard:connect`、`standard:disconnect`、`standard:events`、`solana:signMessage`、`solana:signTransaction`、`solana:signAndSendTransaction`。チェーンは `solana:mainnet`。`legacy` と `v0` の両方のトランザクション形式に対応。 |

:::note SVM レーンに直接アクセスする
同じインターフェースは `window.qorex.svm`（`connect` / `signAndSendTransaction` / `signMessage`）でも利用できます。Wallet Standard による自動検出と完全に実装された SVM レーンは **0.1.5** で追加され、Chrome と Firefox の両方で提供されています([どのバージョンがどこで提供されているか](#versions)を参照)。

Solana の承認画面では、内容が解読されたペイロード(System 転送であれば受取人とラムポート数、それ以外はプログラムの一覧)が表示され、あなたのウォレットが署名者として含まれていないトランザクションは拒否され、署名は**従来型(classical)**として明示されます — [耐量子署名](#pqc)を参照してください。
:::

## 言語 {#language}

この拡張機能は、モバイルアプリ、Dashboard、公式サイトと同じ 10 言語に対応しています。英語、ルーマニア語、ドイツ語、スペイン語、フランス語、イタリア語、トルコ語、アラビア語、日本語、韓国語です。デフォルトでは**ブラウザ**の言語に従います(それ以外の言語の場合は英語にフォールバック)。これはモバイルアプリが**端末**の言語に従うのとは異なる基準であるため、スマートフォンとブラウザで設定言語が異なると、両者で表示言語が食い違うことがあります。ポップアップの待機画面にある言語ピッカーからは、いつでも検出された言語を上書きできます。アラビア語に切り替えると、テキストだけでなくポップアップ全体が直ちに右から左(RTL)のレイアウトに変わります。

## セキュリティとパーミッション {#security}

QoreX は、単に信頼してもらうのではなく、検証できるように作られています。

- **保管領域(vault)** — 鍵は **AES-256-GCM** で封印されます。パスワード方式では **Argon2id**(RFC 9106、メモリハード: 64 MiB、t=3、p=1)で鍵を導出するため、盗まれた保管領域データも GPU/ASIC による解読に耐性を持ちます。(旧来の PBKDF2 形式のデータも引き続き開くことができ、次回のロック解除時に Argon2id へ再封印されます。)
- **パスキーによるロック解除(任意、0.1.5 以降)** — お使いの認証器が **WebAuthn PRF** 拡張に対応している場合、QoreX はパスワードの入力の代わりに、パスキーの 32 バイトの PRF 出力から保管領域をロック解除できます。パスワードは常にフォールバックとして残ります。

  :::note パスキーによるロック解除が表示される条件
  QoreX は WebAuthn を機能検出し、ブラウザが拡張機能のページに対してそれを公開している場合にのみ、**パスキーロック解除を有効にする**を表示します。それが該当するのは**Chrome と Edge**です。**Firefox** ではこのオプションは表示されません。Firefox は拡張機能のページに WebAuthn を公開していないためで、これは想定どおりの動作であり不具合ではありません。
  :::
- **Manifest V3 + 厳格な CSP** — `script-src 'self'; object-src 'self'; base-uri 'self'`。インストール後に**リモートコードを読み込むことは一切なく**、`wasm-unsafe-eval` も使用しません。
- **アカウント不要、テレメトリなし** — アナリティクスも、トラッキングも、リモートロギングも、サインアップも、メールアドレスの登録も一切ありません。Firefox のストア掲載情報でも、データ収集は `none` と申告されています。

### QoreX が要求するパーミッションと、その理由 {#permissions}

このセクションが存在する理由は、Firefox のストア掲載情報にパーミッション**「すべての Web サイトのデータへのアクセス」**が表示されるためです。これは、ホストパーミッションを一切申告していないウォレットにしては矛盾しているように見えるかもしれません。以下は、マニフェストに基づく脚色のない事実です。

拡張機能の `manifest.json` は次のように宣言しています。

```json
"permissions": ["storage"],
"host_permissions": [],
"content_scripts": [
  { "matches": ["<all_urls>"], "js": ["dist/content.js"], "run_at": "document_start" }
]
```

- **`permissions: ["storage"]`** — 唯一の API パーミッションです。暗号化された保管領域データと、オリジンごとの接続承認情報を、**ローカルの**拡張機能ストレージに保存するために使用します。
- **`host_permissions: []`** — QoreX はホストパーミッションを**一切**宣言していません。任意のサイトに対してあなたの代わりにクロスオリジンのネットワークリクエストを行う権限は要求していません。
- **`content_scripts` の `matches` に `<all_urls>` を指定** — これが、Firefox が「すべての Web サイトのデータへのアクセス」と表示する正直な理由です。QoreX は小さなプロバイダスクリプト(`content.js` → `inpage.js`)を**すべてのページ**に注入します。すべてのサイトで動作するコンテンツスクリプトは、技術的にはページを読み取ることが*できる*ため、それが `host_permissions` によるものであれ、コンテンツスクリプトのマッチングによるものであれ、ブラウザはこの能力をこの文言で説明します。

**なぜコンテンツスクリプトがすべてのページで動くのか。** それは、あなたがサイトごとに事前アクセスを許可しなくても、**あらゆる** dApp が EIP-6963 を通じてウォレットを検出できるようにするためです。これは MetaMask、Keplr、Phantom をはじめとする他のすべての注入型ウォレットと同じ仕組みです。注入されるプロバイダは、訪れたどのサイトであっても、そのページのスクリプトが実行される前(`document_start`)に存在している必要があります。

**このスクリプトが行うこと、行わないこと。** このスクリプトはウォレットのメッセージを橋渡しするだけです(プロバイダの告知、接続/署名リクエストの service worker への転送、結果の返送)。それ以外にページの内容を読み取ることは**なく**、サーバーへ何かを送信することも、リモートコードを読み込むこともありません。またホストパーミッションがないため、任意のクロスオリジンデータを取得することもできません。これらはすべて検証可能です。拡張機能は CSP でロックされており、アナリティクスは一切搭載されておらず、Firefox 版のパッケージには再現可能なソースコードの zip が同梱されています。

## dApp を QoreX に接続する {#connect}

dApp は **EIP-6963** を通じて QoreX の EVM レーンを検出します。告知(announce)とリクエストを行い、返された EIP-1193 プロバイダを使用します。

```ts
import type { EIP6963ProviderDetail } from "./types";

const wallets = new Map<string, EIP6963ProviderDetail>();

// 1. Collect every wallet that announces itself.
window.addEventListener("eip6963:announceProvider", (event) => {
  const detail = (event as CustomEvent<EIP6963ProviderDetail>).detail;
  wallets.set(detail.info.rdns, detail);
});

// 2. Ask installed wallets to announce.
window.dispatchEvent(new Event("eip6963:requestProvider"));

// 3. Pick QoreX by its rdns and use the standard EIP-1193 provider.
const qorex = wallets.get("network.qore.qorex");
if (qorex) {
  const accounts = await qorex.provider.request({ method: "eth_requestAccounts" });
  console.log("QoreX EVM account:", accounts[0]);
}
```

QoreChain の **Native** レーンには、`window.qorex.native` にある Keplr 方式のプロバイダ(`enable`、`getKey`、`signDirect`)を使用してください。より高レベルな [`@qorechain/connect`](/sdk/overview) パッケージが、この検出処理をラップしてくれます。

承認は**オリジンごと**に行われます。あるサイトへの最初の接続では、そのオリジンを示す承認ポップアップが開き、承認しても公開されるのは公開アドレスのみで、あるサイトへの承認が別のサイトに何かを許可することはありません。

### Dashboard ブリッジ(v0.1.5) {#dashboard-bridge}

バージョン 0.1.5 では、**`dashboard.qorechain.io` にのみ**適用範囲を限定したブリッジが追加されています。`window.qorex.native.connectProof(sessionId)` は *Connect with QoreX* のペアリング証明に署名し(バックエンド側で署名を再検証します)、`executeTransfer({ to, amountUqor, memo })` は Dashboard から提案された QOR 送金を承認・ブロードキャストし、`txHash` を返します。これらのメソッドは、他のいかなるオリジンからの呼び出しも拒否されます。

`qor1…` アドレスはメインネットとテストネットの両方で等しく有効であるため、Dashboard から提案されるリクエストには対象のネットワークが明記されます。QoreX は、それが拡張機能が現在接続しているネットワークと一致しない場合、そのリクエストの実行を拒否します。リクエストを理由に拡張機能側からネットワークを切り替えることは決してありません。

## 耐量子署名 {#pqc}

QoreX 自身が開始するすべての QOR 送金は、**ハイブリッド耐量子署名**で署名されます。すなわち **ML-DSA-87**(Dilithium-5、NIST **FIPS-204**)と従来型の secp256k1 署名を組み合わせたもので、`@qorechain/sdk` に実装された完全なハイブリッドパイプラインを使用します。**切り替えスイッチは存在しません**。QoreChain がこれを必須としており、QoreX が耐量子署名なしで Native レーンの QOR 送金を送信することは決してありません。

- **dApp が開始する Native レーンの署名** — qorechain-connect のフローに基づいて構築された dApp は、`signDirect` を呼び出す前にトランザクション本体へ PQC 拡張(`/qorechain.pqc.v1.PQCHybridSignature`)をあらかじめ組み込みます。QoreX は従来型の署名部分を提供し、**盲目的な署名(ブラインドサイン)は拒否**します。ペイロードの内容を解読し、PQC レイヤーが存在するかどうかを明示します。
- **従来型のリクエストは必ずラベル表示される** — リクエストに PQC レイヤーが含まれていない場合、または(PQC レイヤーを扱えない)ETH や BNB などの外部チェーンを対象としている場合、QoreX は黙って格下げすることなく、明示的な警告を表示します。

**これがトランザクションサイズに与える影響。** ML-DSA-87 は大きな署名です。署名は **4,627 バイト**、公開鍵は **2,592 バイト**(いずれも FIPS-204 で固定)です。そのため、ハイブリッドな QoreChain トランザクションは、純粋に従来型のトランザクションよりも数キロバイト大きくなります。自分でトランザクションを構築・ブロードキャストする場合は、この追加バイト数を見込んでバッファとガス見積もりのサイズを設計してください。QoreChain のガス計算はすでにこれを織り込み済みです。プリミティブと決定的署名(deterministic signing)の要件については、[耐量子署名](/developer-guide/post-quantum-signing) を参照してください。
