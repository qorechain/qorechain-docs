# ロールアップ開発キット

`x/rdk` モジュールは、開発者が QoreChain 上にアプリケーション固有のロールアップをデプロイできる包括的なロールアップ開発キット (RDK) を提供します。4 つの決済パラダイム、複数のシーケンサーモード、プラグイン可能なデータ可用性バックエンド、AI 支援による構成最適化をサポートします。

:::caution 初期段階の機能
このモジュールはメインネット（チェーンバージョン: 2026 年 10 月 23 日から **v3.2.4**）とテストネット（2026 年 10 月 27 日から **v3.2.6**）にデプロイされていますが、**どちらのネットワークでもロールアップはまだ作成されていません**（2026 年 10 月 27 日に確認: `GET /qorechain/rdk/v1/rollups` は両方で空のリストを返します）。以下に記載する機能のいくつかは、現時点ではエンドツーエンドで使用できません。ステータスは、それぞれの機能を説明する箇所に記載しています。開発者向けのハウツーについては、[ロールアップの概要](/rollups/overview) を参照してください。
:::

---

## 決済パラダイム

QoreChain RDK は、**optimistic**、**zk**、**based**、**sovereign** という 4 つの異なる決済モードをサポートしており、それぞれ異なる信頼前提、ファイナリティ特性、証明要件を持ちます。

### Optimistic 決済 {#optimistic-settlement}

Optimistic ロールアップは、トランザクションがデフォルトで有効であると仮定し、紛争解決のために不正証明 (fraud proof) に依存します。

* **証明システム**: インタラクティブな不正証明
* **チャレンジウィンドウ**: 604,800 秒 (デフォルト、7 日間)。**v3.2.4 より前:** チェーンはこれを 1 ブロックあたり 6 秒の固定レートでブロック数に変換し、**100,800 ブロック**になります。実際の経過時間は実際のブロック時間に依存します (メインネットの現在の約 3.1 秒ブロックでは約 3.7 日)。そのため、日数ではなくブロック数で計画してください。**v3.2.4 以降:** アップグレード高さ以降に提出されたバッチでは、ウィンドウはブロック時間の秒数で計測されます (丸 7 日間)。それより前に提出されたバッチは、ブロック数のルールのままです。テストネットは v3.2.4 を高さ 8,337,253（2026 年 10 月 19 日）で適用しました。メインネットは高さ 3,742,566（2026 年 10 月 23 日、ガバナンス提案 13）で適用しました。テストネットの設定済みデフォルトはそれより短い 3,600 秒（1 時間）であるため、テストネットのロールアップは、ここで説明している 7 日間よりも早くファイナライズされます。
* **チャレンジボンド**: 1,000 QOR (1,000,000,000 uqor) — 不正証明チャレンジの提出に必要 (`nft` および `custom` プリセット。`defi`、`gaming`、`enterprise` プリセットはチャレンジウィンドウがないため、ボンドを設定しません)
* **ファイナリティ**: 有効なチャレンジがないままチャレンジウィンドウが終了するまで遅延
* **自動ファイナライズ**: `EndBlocker` は、チャレンジウィンドウが紛争なく経過すると、バッチを自動的にファイナライズします。チャレンジされたバッチが自動的にファイナライズされることはありません。先に解決される必要があり、メインネット(v3.2.4)ではロールアップの作成者が、テストネット(v3.2.5 以降)では任意のアカウントが解決します(メインネットは、ガバナンス提案 14 が v3.2.5 を適用した時点で追随します) ([ロールアップのデプロイ](/rollups/deploying-a-rollup#challenge-a-batch-optimistic-rollups) を参照)。

**バッチライフサイクル**:

```
Submitted → [challenge window expires] → Finalized
Submitted → [fraud proof submitted] → Challenged → Rejected
```

### ZK (ゼロ知識) 決済 {#zk-zero-knowledge-settlement}

ZK ロールアップは、状態遷移の正しさを保証する暗号学的妥当性証明を提供します。

* **証明システム**: SNARK (BLS12-381 上の Groth16) または STARK (透過的、トラステッドセットアップ不要)
* **ファイナリティ**: 証明検証時に即座に確定 — チャレンジウィンドウは不要
* **最大証明サイズ**: 1 MB (1,048,576 バイト)
* **再帰深度**: 設定可能な証明集約深度 (デフォルト: 1)
* **成熟度**: SNARK バッチは、ロールアップとともに保存された検証鍵に対してオンチェーンで検証されます (BLS12-381 上の Groth16)。**ZK 決済は、現時点ではどちらのネットワークでも使用できません。** チェーンにはロールアップの検証鍵を登録する手段がないため、すべての ZK バッチは手数料が支払われた後に拒否されます。鍵の登録はチェーン v3.2.7 で予定されています。STARK 検証は実験的なものです。オプトイン方式で、ロールアップ自身の状態遷移ではなくデモンストレーション用の回路を検証します。ZK 決済は本番環境向けではないものとして扱ってください。

**バッチライフサイクル**:

```
Submitted + valid proof → Finalized (instant)
```

### Based 決済

Based ロールアップは、トランザクションのシーケンシングを L1 (QoreChain) プロポーザーに委譲し、ホストチェーンのライブネスと検閲耐性の保証を継承します。

* **証明システム**: 不要 — L1 プロポーザーが信頼の源泉
* **シーケンサー**: `based` シーケンサーモードを使用する必要があります (検証により強制)
* **ファイナリティ**: QoreChain 上で 2 ブロックの確認
* **インクルージョン遅延**: ロールアップトランザクションの強制インクルージョンまでの設定可能なブロック数
* **優先手数料の分配**: L1 プロポーザーに支払われる優先手数料の設定可能な割合

**バッチライフサイクル**:

```
Submitted → [2 L1 blocks] → Finalized (auto)
```

### Sovereign 決済

Sovereign ロールアップは独立したコンセンサスで動作し、自身のトランザクションを自己シーケンシングします。検証可能性のために状態を QoreChain にアンカーしますが、ファイナリティをホストチェーンに依存しません。

* **証明システム**: なし
* **ファイナリティ**: 独立 — ロールアップ自身のコンセンサスによって決定
* **状態アンカリング**: 状態ルートは透明性と検証可能性のために QoreChain に投稿されますが、強制はされません
* **自動ファイナライズ**: なし — Sovereign ロールアップは独自のファイナリティを管理します

## 証明システムの互換性

| 決済モード       | 不正証明     |     SNARK |     STARK |     なし |
| --------------- | -----------: | --------: | --------: | -------: |
| **Optimistic**  |     必須     |        -- |        -- |       -- |
| **ZK**          |           -- | 対応      | 対応      |       -- |
| **Based**       |           -- |        -- |        -- | 必須     |
| **Sovereign**   |           -- |        -- |        -- | 必須     |

STARK 検証は実験的であり、ZK 決済は本番環境向けではありません。上記の [ZK 決済](#zk-zero-knowledge-settlement)の成熟度に関する注記を参照してください。

## プリセットプロファイル

RDK は、一般的なユースケースに最適化されたターンキー型のロールアップ構成を提供する **5 つのプリセットプロファイル**を同梱しています。各プリセットは、対象ドメインに合わせて調整された決済パラダイム、シーケンサーモード、データ可用性バックエンド、ガスモデル、VM をバンドルしています:

| プロファイル      | 決済 (証明)              | シーケンサー | DA              | ガスモデル   | VM      | 対象ユースケース |
| ---------------- | ------------------------ | --------- | --------------- | ------------ | ------- | --------------- |
| **`defi`**       | zk (SNARK)               | dedicated | native          | EIP-1559     | EVM     | トレーディング、レンディング、AMM 型アプリケーション |
| **`gaming`**     | based                    | based     | native          | flat         | custom  | 高スループット・低レイテンシのゲーム状態とゲーム内経済 |
| **`nft`**        | optimistic (fraud)       | dedicated | native (Celestia DA 計画中) | standard | QoreChain Native | NFT のミント、マーケットプレイス、デジタルコレクティブル |
| **`enterprise`** | based                    | based     | native          | subsidized   | EVM     | 手数料がスポンサードされる許可制およびコンソーシアム型デプロイメント |
| **`custom`**     | 完全にパラメータ化       | 完全にパラメータ化 | 完全にパラメータ化 | 完全にパラメータ化 | 完全にパラメータ化 | すべてのフィールドがユーザー定義 |

`custom` プロファイルでは、すべてのフィールドを自分で設定します。各プリセットにバンドルされる正確な値は RDK の成熟に伴って変化する可能性があります。権威あるプリセットごとのパラメータについては、`qorechaind query rdk config` (または `@qorechain/rdk` の `RdkClient.params()`) でライブ構成をクエリしてください。また、`based` 決済は常に `based` シーケンサーモードとペアになることに注意してください。

## シーケンサーモード

シーケンサーは、ロールアップブロック内でトランザクションを順序付けする者を決定します。

:::note 現時点で強制されているもの
オンチェーンでは、バッチを提出できるのは、ロールアップに設定されたシーケンサーアドレス、または設定されていない場合 (すべてのプリセットが該当) はその作成者のみです。`shared` モードと `based` モードはロールアップ構成に記録されますが、QoreChain はまだ共有シーケンサーの名簿や L1 プロポーザーをバッチ提出者として受け入れていません。これらのモードは意図された設計を記述したものです。
:::

### Dedicated シーケンサー

単一のオペレーターがすべてのロールアップトランザクションをシーケンシングします。

* **オペレーター**: 単一の指定アドレス
* **レイテンシ**: 可能な限り最低 — 単一当事者による順序付け
* **信頼**: ライブネスと公正な順序付けについてシーケンサーオペレーターへの信頼が必要

### Shared シーケンサー

シーケンサーのセットが集合的にトランザクションを順序付けします。

* **ステータス**: 現時点ではラベルのみ — 名簿はまだオンチェーンで受け入れられていません (上記の注記を参照)
* **最小セットサイズ**: 設定可能 (デフォルト: 1)
* **レイテンシ**: 複数当事者の調整によりわずかに高い
* **信頼**: シーケンサーセット全体に分散

### Based シーケンサー

QoreChain L1 プロポーザーがロールアップトランザクションをシーケンシングします。

* **ステータス**: 現時点ではラベルのみ — L1 プロポーザーはまだバッチ提出者として受け入れられていません (上記の注記を参照)
* **インクルージョン遅延**: 強制インクルージョンまでの設定可能なブロック数 (デフォルト: 10)
* **優先手数料シェア**: L1 プロポーザーに支払われる優先手数料の設定可能な割合
* **信頼**: QoreChain のバリデーターセットのセキュリティと検閲耐性を継承
* **要件**: Based 決済モードは Based シーケンサーを必要とします (検証時に強制)

## データ可用性バックエンド

### Native DA

QoreChain 自体の中のオンチェーン KV ストアによる blob ストレージ。

:::caution blob を投稿する公開手段はまだありません
このモジュールは blob のストレージ、保持、プルーニングを定義していますが、現在のリリースには blob を投稿するためのトランザクションメッセージがありません。`native` または `both` のロールアップでデータハッシュを指定したバッチは、対応する blob を保存できないため拒否されます。[データ可用性](/rollups/data-availability) を参照してください。そのため、ネイティブなデータ可用性ではバッチの `data_hash` を空にする必要があります。RDK クライアント(0.7.0)はそのようにしており、チェーンはデータハッシュを主張するバッチを拒否します。
:::

| パラメータ           | 値                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **最大 blob サイズ** | 2 MB (2,097,152 バイト)                                                                              |
| **保持期間**         | 432,000 ブロック (メインネットの現在の約 3.1 秒ブロックで約 16 日。この数値はブロック時間に応じて変動します) |
| **自動プルーニング** | 期限切れの blob は `EndBlocker` でプルーニングされます — データは削除されますが、コミットメントのメタデータは保持されます  |
| **コミットメント**   | blob データの SHAKE-256 (32 バイト) ハッシュ                                                     |

### Celestia DA

Celestia の専用 DA レイヤーを使用した IBC ベースのデータ可用性。

* **ステータス**: 現在のリリースではスタブ化されています — 唯一のバックエンドとして選択された場合はエラーを返します
* **ネームスペースサポート**: ロールアップ固有のネームスペースが blob スキーマでサポートされています
* **計画中**: Celestia の blob 提出と検証による完全な IBC 統合

### Both (冗長)

Native と Celestia の両方のバックエンドに同時に blob を保存します。

* 現在のリリースでは、実際に保存されるのは native の blob のみであり、Celestia コンポーネントについては警告がログに記録されます。

## ロールアップのライフサイクル

```
Pending → Active → Paused → Active → Stopped
                      ↑                  |
                      └──────────────────┘
                      (can resume from paused,
                       stopped is permanent)
```

| 状態        | 説明                                                  |
| ----------- | ------------------------------------------------------------ |
| **Pending** | ロールアップは登録済みだがまだアクティブ化されていない                      |
| **Active**  | ロールアップは稼働中でバッチを処理している                        |
| **Paused**  | 作成者によって一時的に停止 (再開可能)                   |
| **Stopped** | 恒久的に廃止 — 作成者のエスクローに残っているものは返却される ([エスクロー台帳](#escrow-ledger) を参照)  |

作成時、ステークのエスクローと作成時バーンが成功すると、ロールアップのステータスは直ちに `Active` に設定されます (レイヤー登録は試行されますが、致命的ではありません)。ロールアップを一時停止、再開、または停止できるのは作成者のみです (チェーンバージョン v3.2.0 以降で強制)。

## バッチのライフサイクル

決済バッチは、ロールアップの状態ルートの状態進行を追跡します:

```
Submitted → Finalized                              (happy path)
Submitted → Challenged → Rejected                  (fraud detected)
```

| 状態           | 説明                                       |
| -------------- | ------------------------------------------------- |
| **Submitted**  | バッチが QoreChain に投稿され、ファイナライズ待ち  |
| **Challenged** | 不正証明チャレンジが提出された (optimistic のみ) |
| **Finalized**  | バッチが正規のものとして受け入れられた                       |
| **Rejected**   | 成功したチャレンジによりバッチが無効化された         |

RDK 0.6.1 以降の動作(現行は 0.7.0):optimistic ロールアップの場合、クライアントは、ステートルートがチェーンの正規の遷移ルート(RDK の `batchTransitionRoot`)であるバッチを構築します。ご自身で決めた自由形式の値ではありません。

### 自動ファイナライズのルール

| 決済モード       | ファイナライズのトリガー                                        |
| --------------- | ----------------------------------------------------------- |
| **Optimistic**  | 提出から 100,800 ブロック後 (デフォルトのウィンドウ)、チャレンジなし。v3.2.4 以降に提出されたバッチ（テストネットは高さ 8,337,253 から、メインネットは高さ 3,742,566、2026 年 10 月 23 日から）については、ブロック時間で 604,800 秒 |
| **ZK**          | 有効な証明の提出時に即座に確定                           |
| **Based**       | 提出後 2 つの L1 ブロック                                |
| **Sovereign**   | なし — ロールアップ自身のコンセンサスにより管理                |

自動ファイナライズは、optimistic および based ロールアップでは `EndBlocker` で実行されます。ZK バッチは、バッチ提出中にインラインでファイナライズされます。

## マルチレイヤー統合

RDK モジュールは、クロスレイヤー状態管理のために `x/multilayer` と統合されています:

### レイヤー登録 {#layer-registration}

ロールアップが作成されると、モジュールは `RegisterSidechain` を通じてそのためのレイヤーを登録します。そのため、オンチェーンではレイヤータイプは **`sidechain`** となり、`proposed` ステータスで開始され、multilayer のサイドチェーン上限 (`max_sidechains`、デフォルト **10**) にカウントされ、作成者の `min_sidechain_stake` (1,000 QOR) をロックします。登録には以下が含まれます:

* レイヤー ID (ロールアップ ID と一致)
* ターゲットブロック時間とブロックあたりの最大トランザクション数
* サポートされる VM タイプとドメイン
* 決済間隔

登録は**致命的ではありません**: 失敗した場合 (残高不足または上限到達)、ロールアップは作成されますが、レイヤーを持たず、アンカーできません。決済アンカーはレイヤーが `active` であることを必要としません。RDK ロールアップが登録するレイヤーは `proposed` のままで、その作成者がアンカーすることができます ([アンカーの送信](/architecture/multilayer-architecture#anchor-submission) を参照)。

### 状態アンカリング {#state-anchoring}

決済バッチは `x/multilayer` にアンカーでき、レイヤー ID、レイヤーの高さ (バッチインデックス)、状態ルート、バリデーターセットのハッシュ、トランザクション数が、ロールアップ作成者によるポスト量子署名のもとで記録されます。

* **v3.2.2 以降 (メインネットとテストネットで稼働中):** `MsgSubmitBatch` には 2 つの任意フィールドがあります。`anchor_signature` は、バッチの **v2 アンカー署名バイト** (詳細は [アンカーの読み取り](/architecture/multilayer-architecture#reading-anchors) を参照) に対する作成者の ML-DSA-87 署名です。これが存在する場合、バッチは**同じトランザクション**内で `x/multilayer` にアンカーされ、アンカーが拒否されるとバッチも拒否されます。`validator_set_hash` は、アンカーに含まれて署名の対象となる、ロールアップのバリデーターセットのコミットメントです。CLI では、`qorechaind query rdk anchor-sign-bytes <layer-id> <batch-index> <state-root-hex> --chain-id <id> --tx-count <n>` が署名対象のバイト列を出力し（`<layer-id>` はロールアップのレイヤー ID で、RDK 経由で作成されたロールアップではロールアップ ID と同じです）、`tx rdk submit-batch ... --anchor-signature <hex> --validator-set-hash <hex>` がそれらを送信します。
* **署名なしの場合**、バッチはこれまでどおりアンカーされずに決済されます。このフィールドを送信しないクライアントはアンカーされないバッチを生成するため、使用しているツールキットがこれをサポートしているか確認してください。TypeScript の `@qorechain/rdk` 0.6.0 は、クライアントがハイブリッド署名を行い、かつロールアップの作成者である場合にアンカーへ署名します（それ以外の場合はアンカーなしで送信します）。一方、Python、Go、Rust、Java のクライアントはこのフィールドを組み立てません。どちらのネットワークにも、ロールアップ、レイヤー、アンカーはまだ存在しないため、アンカーは一度も書き込まれておらず、その経路は実ネットワークでは未テストです。

アンカーが何を証明し、何を証明しないかについては、[決済レシート](/rollups/settlement-receipts) を参照してください。

## エスクロー台帳と出金 {#escrow-ledger}

すべてのロールアップのエスクローは、1 つのプールされたモジュール残高に置かれています。**v3.2.3**（メインネットの高さ 3,662,051、2026 年 10 月 20 日）以降、ロールアップごとの**エスクロー台帳**が、そのプールで各ロールアップが保有するものを管理する唯一の帳簿です。

* `create-rollup` は、ロールアップが実際に保持するエスクロー、つまりステークから 1% の作成時バーンを差し引いた額を台帳に計上します。
* 出金 (`tx rdk execute-withdrawal`) と不正証明の報酬は、台帳から支払われ、台帳から差し引かれます。ロールアップがまだ保有している額を超える出金は、エスクロー不足のエラーで拒否されます。
* `stop-rollup` は、台帳に残っている分だけを返金し、台帳をゼロにします。停止されたロールアップは、それ以降の出金を支払いません。
* ロールアップのクエリが返す読み取り専用の `RollupView` は `escrow_balance` を保持しています。これは、そのロールアップのためにまだ保有されている uqor です。

v3.2.3 より前は、台帳にはゼロが計上されていたため、すべての出金がフェイルクローズで失敗していました。したがって、メインネットで `execute-withdrawal` が成功しうるのは v3.2.3 以降のみです。クライアントが手数料を支払う前に確認すべき事項: デノミネーションは正確に `uqor` であること、金額が正であること、Merkle 証明は最大 64 レベルで、すべての兄弟ノードがちょうど 32 バイトであること、提出者と受取人が有効な `qor1…` アドレスであること。出金には、`withdrawals_root` をコミットしたファイナライズ済みのバッチも必要で、各出金リーフは 1 回しか支払われません。

## RDK の状態の読み取り {#reading-state}

RDK のクエリは、メインネットとテストネットで `/qorechain/rdk/v1/` 配下の REST で提供されています。

| ルート | 返すもの |
| --- | --- |
| `/params` | モジュールパラメータ（上記の表） |
| `/rollups` および `/rollup/{rollup_id}` | `escrow_balance` を含むロールアップのレコード |
| `/batches/{rollup_id}` | ページングされたバッチ（`start_index`、`limit` はデフォルト 50、最大 100、`next_index`） |
| `/batch/{rollup_id}/{batch_index}` および `/latest_batch/{rollup_id}` | 1 件のバッチ、または最新のバッチ |
| `/blob/{rollup_id}/{blob_index}` | `expires_at_height` を含む blob のメタデータ（blob のバイト列は返されません） |

`qorechaind query rdk config` はモジュールパラメータを出力します（ルートは `/params` で、`/config` というルートはありません）。ロールアップ ID とレイヤー ID は、v3.2.2 以降強制されている[レイヤー ID とロールアップ ID](/architecture/multilayer-architecture#id-grammar)の文法に一致する必要があります。

## バーン統合

ロールアップ作成時、**ステーク額の 1%** が `rollup_create` バーンチャネルを通じて `x/burn` モジュール経由でバーンされます。例えば、最小 10,000 QOR のステークでロールアップを作成すると、100 QOR が恒久的にバーンされます。残りの 9,900 QOR はエスクローに保持され、ロールアップが停止されたときに、その残額が作成者に返却されます (エスクローから支払われた出金と不正証明の報酬は、返金額を減らします)。作成時のバーンはチェーンバージョン v3.2.0 以降で強制されており、以前のリリースでは適用されていませんでした。
