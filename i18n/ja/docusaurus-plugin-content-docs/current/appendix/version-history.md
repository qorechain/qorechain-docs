# バージョン履歴

QoreChain の公開バージョン履歴です。最新リリースは **v3.1.95** で、メインネット **`qorechain-vladi`**(EVM チェーン ID **9801**、2026年6月7日稼働開始)上で動作しています。テストネット **`qorechain-diana`**(EVM チェーン ID **9800**)はプレリリースビルドを追跡します。

:::note
以下のエントリは高レベルの機能サマリーです。初期の `v1.x` エントリは、メインネット以前のテストネットリリースラインの歴史的記録として保持されています。
:::

---

## v3.1.95 — Cosmos EVM ハードニング(現行リリース)

**リリースの焦点:** EVM 残高会計ライブラリに対するローリングセキュリティアップデート。

* **オーバーフロー対策の強化** — EVM の残高更新パスは、極端なオーバーフロー条件下で黙ってラップアラウンドするのではなく、安全に失敗するようになりました。コンセンサスを壊さないローリングアップデートとして提供され、ガバナンス投票や協調ハルト高さは不要でした。

## v3.1.94 — 発行上限と管理系メッセージのハードニング

**リリースの焦点:** ステーキング報酬の発行量を実際のネットワーク状況に合わせ、権限付き管理系メッセージの認可チェックを強化。

* **発行上限** — 完全なボンド済みステークの支持を得て可決されたガバナンス提案が、高さ 2,122,074(2026年8月26日)で適用され、元の逓減型発行スケジュールを、確定した累積上限のもとでのエポックごとの固定額に置き換えました。元のスケジュールは、はるかに成熟した完全ボンド状態のネットワークを想定して調整されていたため、実際のボンド済みステークに対しては想定よりはるかに速いペースで支払われていました。現在の数値と残りのランウェイについては[トークノミクス](/architecture/tokenomics#staking-reward-schedule)を参照してください。
* **管理系メッセージのハードニング** — 権限付き・認可ゲート付きの一連の管理系メッセージについて、署名者の検証が、メッセージ自体に含まれる値を信頼するのではなく、ガバナンスモジュール自身のアドレスと照合して行われるようになりました。
* このリリースへ直接アップデートするノードのために、v3.1.92 のノードオンボーディング信頼性の修正も引き続き含まれています。

## v3.1.92 — ノード同期の信頼性向上

**リリースの焦点:** スナップショットおよび公開チェーンアーカイブからのノードオンボーディングの信頼性向上。

* **スナップショット/アーカイブ同期の修正** — ステートシンクのスナップショットまたは公開チェーンアーカイブから復元するノードが、特定の過去のブロックを超えて同期を完了できなくなる問題を解消しました。いずれの経路によるオンボーディングも確実に完了するようになりました。

## v3.1.90 — ライトノード稼働率の集計

**リリースの焦点:** ライトノードの報酬適格性のために計測される稼働率が、時間経過にわたって一貫して積算されるようになりました。

* **前方積算される稼働率** — ライトノードの報酬適格性の稼働率は、現在有効なハートビート間隔を使ってその全履歴を再計算するのではなく、そのノード自身の登録時点から、各時点で有効だったハートビート間隔に基づいて期待されるハートビート数を前方に積算することで算出されるようになりました。したがって、ハートビート間隔へのガバナンス変更は今後の稼働率にのみ影響し、ノードの過去の実績を遡って再評価することはありません。

## v3.1.86 — バリデーター復旧のセーフガード

**リリースの焦点:** バリデーターがダウンタイムジェイルからの復旧に永続的に失敗する状態を防止。

* **ジェイルロックの修正** — ポスト量子鍵を未登録のバリデーターオペレーターアカウントは、ハイブリッド署名の強制が「必須(古典署名フォールバック無効)」に設定されている場合でも、ダウンタイムジェイルからの復旧のために常に `MsgUnjail` を送信できるようになりました。以前は、ジェイル解除自体に送信をブロックされているトランザクションの送信が必要だったため、そのようなアカウントには復旧手段がありませんでした。
* **ステートシンクスナップショット** — スナップショット生成がネットワーク全体で有効化され、新規バリデーターおよびフルノードが完全な過去のリプレイではなくステートシンクによって高速に参加できるようになりました。

## v3.1.85 — 連携ウォレットによる委任支出

**リリースの焦点:** 連携された外部ウォレット鍵(Phantom、MetaMask)が、最小権限の許可・支出上限・即時失効のもとで、単一の正規のポスト量子アカウントから**支出**できるようになりました。

* **オーセンティケーター実行レーン** — 2つの新しいメッセージにより、登録済みのオーセンティケーターが、アカウント所有者が不在でも正規アカウントからの送金を許可できるようになりました。**`MsgExecuteEVM`**(アカウントの `0x…` アドレスからの EVM コール/送金)と **`MsgExecuteCosmos`**(Native レーンでのバンク送金)です。**リレイヤー**がエンベロープを送信・手数料負担します(リレイヤー自身のハイブリッド PQC 署名がトランザクション要件を満たします)。一方、ドメイン分離されリプレイに紐づいた署名対象バイト列に対するオーセンティケーターの署名が認可となります。外部鍵に ML-DSA による共同署名は一切不要です。
* **オーセンティケーターとしての MetaMask** — secp256k1 オーセンティケーターは、33バイトの圧縮鍵形式に加えて、**20バイトの Ethereum アドレス**として登録し、**EIP-191 `personal_sign`** で検証できるようになりました。これにより、標準的な MetaMask アカウントを連携させ、上限の範囲内で支出させることができます。
* **3レーンすべてでの権限強制** — 許可スコープと **SpendingRule** による金額上限(トランザクションごと・日次上限)は、Native、EVM、SVM の各レーンで強制され、鍵管理系メッセージは決して委任できません。個別のエラーコードにより、ウォレット側で適切なメッセージを表示できます:`5` 支出上限超過、`6` オーセンティケーター期限切れ、`10` 権限拒否、`11` リプレイ拒否。
* **権限スキーマクエリ** — `GET /qorechain/abstractaccount/v1/permission_schema`(gRPC/CLI でも利用可)は、正規の権限タクソノミー(11 種類の権限)、メッセージから権限へのマッピング、および委任不可メッセージの一覧を返すため、ウォレットはスコープをハードコードせずに検証できます。
* **同一アルゴリズムでの PQC 鍵ローテーション** — 新しい **`MsgRotatePQCKey`** は、アカウントの ML-DSA-87 鍵を同一アルゴリズム内でローテーションします(旧鍵と新鍵の両方による二重署名)。これにより、レガシー方式で導出された鍵を正規のアドレス紐づけ導出方式へ移行させたり、漏えいした鍵を失効させたりできます。新しい CLI:`tx pqc rotate-key` および `tx pqc recover-key`(ニーモニックからの決定論的な鍵復元)。
* **ルート鍵トランザクションへの影響なし** — 今回の変更は加算的なもので、通常のウォレット・取引所・Keplr のフローは変わりません。ノードオペレーターは、ネットワークアップグレードの高さまでに **v3.1.85** に移行する必要があります。

## v3.1.84 — オーセンティケーター権限と支出上限

**リリースの焦点:** 委任支出の背後にある権限モデル。

* **正規の権限タクソノミー** — 11 種類の権限(`all`、`send`、`delegate`、`withdraw`、`vote`、`evm`、`wasm`、`svm`、`amm`、`ibc`、`deploy`)と、フェイルクローズなメッセージ→権限マッピング:マッピングされていないメッセージタイプは拒否され、鍵管理系メッセージは決して委任できません。
* **SpendingRule の強制** — 許可デノム一覧付きの、トランザクションごと・日次(UTC)の支出上限が強制され、(アカウント, オーセンティケーター)のペアごとに記録されます。
* **SVM レーンの認可** — 外部方式の鍵(例:Phantom の ed25519)によって SVM レーンで認可されるアクションも、同じ中央認可ゲートを経由します。

## v3.1.83 — 3つのインターフェース全体での統一アカウント署名

**リリースの焦点:** 1つの鍵、1つのアカウント — Cosmos、EVM、SVM の各インターフェースで、残高を保持するだけでなく**署名**もできる、単一の統一アイデンティティ。

* **すべてのレーンで1つの鍵が署名** — eth-native 方式(アドレス = secp256k1 公開鍵の keccak)で作成されたアカウントは、EVM トランザクションに加えて、`eth_secp256k1` 方式で Cosmos レーンのトランザクションにも署名できるようになりました。その `qor1…`(Cosmos)、`0x…`(EVM)、Solana-VM(base58)形式は、1つの残高を**保持**し、3レーンすべてで**支出**できる(ポスト量子ハイブリッド〔ML-DSA-87〕による Cosmos トランザクションを含む)単一の20バイトのアイデンティティです。
* **ポスト量子署名は変更なし** — 統一アカウントは引き続き ML-DSA-87 鍵を登録し、チェーンが要求する FIPS-204 ハイブリッド署名を保持します。古典署名部分はコインタイプ118方式ではなく `eth_secp256k1`(keccak)になります。既存のコインタイプ118アカウントには影響しません。
* **コンセンサスに中立なローリングアップグレード** — 両ネットワークでバイナリのローリングアップグレードとして提供され、**再ジェネシスもチェーン停止もありません**。アカウント残高、履歴、ジェネシスは変更されません。
* **クライアントツール** — `@qorechain/wallet-adapter` 0.1.5 は eth-native な Cosmos 署名(`signClassicalEth` / `signHybridEth`)、統一された3アドレス生成、および `walletFromSeed`(任意の32バイトシード — 例:Phantom の署名 — から正規アカウントを導出)を追加します。`@qorechain/chain-bridge` は `eth_secp256k1` 署名パスを獲得します。

:::caution ノードオペレーター — アップグレード必須
フルノードは **v3.1.83 以降**で稼働する必要があります。v3.1.83 より前のノードは eth-native(`eth_secp256k1`)トランザクションをデコードできず、そのようなトランザクションがブロックに現れると同期が止まります。[download.qore.host](https://download.qore.host) から現行バンドルをダウンロードしてください。
:::

## v3.1.82 — SVM 上のネイティブ QOR 稼働 + インテグレーター対応強化

**リリースの焦点:** 両ネットワークで稼働する SVM ネイティブ QOR 統合と、取引所やインテグレーターの接続に必要なすべて。

* **3つのインターフェースすべてで統一ネイティブ QOR 残高が稼働** — SVM 統合(v3.1.81)がメインネットおよびテストネットで稼働していることを確認しました。同一アカウントが保持する1つの残高は、Cosmos 上では `uqor`(6桁)、EVM 上では wei 方式の18桁、Solana 互換インターフェース上ではランポート(9桁、1uqor = 1,000 ランポート)として表示されます。
* **検証済みの公開エンドポイント** — コンセンサス RPC、REST、EVM JSON-RPC、SVM JSON-RPC の公開 HTTPS エンドポイントが両ネットワークで利用可能になり、公開の[ブロックエクスプローラー](https://explore.qore.network)も利用できます。[ネットワーク](/appendix/networks)を参照してください。
* **ダウンロード** — バージョン管理されたノードバイナリバンドル、メインネットジェネシス、および最新のチェーンデータスナップショット(SHA-256 チェックサム付き)を [download.qore.host](https://download.qore.host) で公開しています。
* **クライアントスタック全体での決定論的なポスト量子署名** — `@qorechain/pqc` 0.1.1 は、チェーンが受け入れる方式に一致する形で、6つすべての言語バインディングにおいて ML-DSA-87 を決定論的に(FIPS-204 §3.4)署名します。`@qorechain/wallet-adapter` 0.1.2 はこれを基盤にハイブリッドトランザクション署名を構築します。
* **インテグレーター向けガイド** — 3つのインターフェースにまたがる入金、出金、ノード運用を扱う新しい[取引所・インテグレーターガイド](/developer-guide/exchange-integration)。

## v3.1.81 — SVM ネイティブ QOR 統合

**リリースの焦点:** Solana 互換インターフェース上でのファーストクラス資産としてのネイティブ QOR。

* **SVM 上のネイティブ QOR** — SVM ランタイムは、別建ての SVM 専用残高を追跡するのではなく、アカウントのネイティブ QOR 残高を(ランポート単位で)直接表示するようになりました。`getBalance` と `getSignaturesForAddress` はネイティブ資金に対して機能し、System Program の送金はネイティブ QOR を動かします。
* **SVM アドレスマッピング** — アカウントの SVM アドレスは、その20バイトのアカウントバイト列(32バイトへ右詰めパディングし base58 エンコード)から導出されるため、1つの鍵の Cosmos、EVM、SVM の各アドレスは同一の資金を指します。

## v3.1.80 — マルチレイヤー・ステートアンカークエリ

**リリースの焦点:** ロールアップ向けの、可読でオフライン検証可能な決済アンカー。

* **アンカー読み取りクエリ** — `x/multilayer` クエリサービスは、`Anchor`(レイヤーの最新ステートアンカー)と `Anchors`(レイヤーのアンカー履歴)を公開するようになり、クライアントはレイヤーの決済アンカーを取得して独立に検証できます。
* **multilayer 向け REST ゲートウェイ** — multilayer のすべてのクエリ(`params`、`layers`、`layers/{layer_id}`、`anchor/{layer_id}`、`anchors/{layer_id}`、`routing-stats`)が、gRPC に加えて REST でも利用可能になりました。
* **量子耐性のある決済レシートが解禁** — 各アンカーはその正規フィールドに対する **ML-DSA-87(Dilithium-5)** 署名を保持し、Rollup Development Kit のオフライン決済レシート検証のオンチェーン基盤を提供します。

## v3.1.79 — ブリッジネットワーク向けバリデーター自動プロビジョニング

**リリースの焦点:** ライセンス済みバリデーターに対する、接続先ネットワークへのターンキー参加。

* **ネットワークドライバーフレームワーク** — 宣言的なドライバーフレームワークにより、該当する `validator_<chain>`(または `qcb_bridge`)ライセンスを保持する QoreChain バリデーターは、そのライセンスが有効化された時点でのみ、対応する外部ネットワーククライアントを同一ノード上に QoreChain のオーケストレーションの下でプロビジョニング・設定・実行させることができます。
* **37の全ブリッジネットワーク向けドライバー** — 接続されているすべてのネットワークをカバーし、参加モデル(パーミッションレスなバリデーター、上限付き/選出/入会制、L2 フルノード、非ステーキング/トラストリスト方式)ごとに分類されています。外部ネットワークのステークと署名鍵は引き続きオペレーターがネットワークごとに用意します。QoreChain はフレームワークと強制的なライセンスゲートを提供します。

## v3.1.78 — デプロイ前レディネス

**リリースの焦点:** デプロイ後のガバナンスを必要とせず、ローンチ時点でウォレット、ブリッジ、IBC、ライセンスがすべて機能する状態。

* **信頼不要のデプロイ後ブリッジ有効化** — `bridge_admin` 鍵(または `qcb_bridge` ライセンス保有者)は、単一の署名付きトランザクション(`tx bridge update-chain-config` / `set-verifier-bootstrap`)により、コントラクトアドレス、確認数、アーキテクチャ、ステータス、アクティブなベリファイア、ベリファイアのトラストルートを設定して、任意の接続先チェーンのブリッジを有効化できます。ガバナンス提案もチェーンアップグレードも不要です。
* **バリデーターネットワークのライセンスゲート** — オーケストレーターは、外部ネットワーククライアントを起動する前に `validator_<chain>` / `qcb_bridge` ライセンス(フェイルクローズ)を強制するようになりました。
* **ウォレット統合パッケージ** — `@qorechain/wallet-adapter` と `@qorechain/connect` が npm に公開されました(v0.1.0)。EVM レール上でのネイティブ QOR **18桁**を用いたワンコールの MetaMask ネットワーク登録(EIP-3085)と、Keplr のガス価格設定が追加されています。
* **IBC ターンキーリレイヤー** — 8つの IBC カウンターパーティ向けに、すぐに使えるリレイヤー設定とチャネルブートストラップツールが用意され、独自のセットアップなしでデプロイ後にチャネルを立ち上げられます。

## v3.1.77 — ブリッジ・バーン REST エンドポイント

**リリースの焦点:** クロスチェーンモジュールおよびサプライモジュールへの読み取り専用 REST アクセス。

* **ブリッジ REST エンドポイント** — bridge モジュール向けの読み取り専用 HTTP クエリエンドポイントで、ブリッジの状態を gRPC に加えて標準的な REST でも公開します。
* **バーン REST エンドポイント** — burn モジュール向けの読み取り専用 HTTP クエリエンドポイントで、手数料分配とサプライのデータを標準的な REST でクエリできるようにします。

## v3.1.76 — SVM ツールチェーンの近代化

**リリースの焦点:** Solana Virtual Machine 互換性の刷新。

* **最新ツールチェーンによるプログラムのサポート** — 現行の Solana ツールチェーンでビルドされたプログラムが QoreChain の SVM ランタイム上で動作するよう、SVM 実行系を刷新しました。

## v3.1.75 — SVM JSON-RPC のデフォルト有効化

**リリースの焦点:** すぐに使える Solana 互換 RPC。

* **Solana 互換 JSON-RPC** — SVM JSON-RPC サーバーがデフォルトで有効化され(ポート **8899**)、ノードとともに自動的に起動するようになり、SVM ツール向けの Solana 互換 RPC インターフェースを提供します。

## v3.1.74 — ロールアッププロファイルのプリセット

**リリースの焦点:** Rollup Development Kit の使いやすさと決済。

* **プロファイルプリセットの適用** — ロールアップの作成時に、選択したプロファイルのプリセット(DeFi、ゲーム、NFT、エンタープライズ、または完全カスタム)が適用されるようになり、新規ロールアップはそのユースケースに適した既定値を継承します。
* **オプティミスティック決済** — オプティミスティック決済パス(バッチ送信とチャレンジ)がエンドツーエンドで稼働します。

## v3.1.73 — ポスト量子ハッシュのベースライン

**リリースの焦点:** デフォルトのポスト量子暗号ベースラインの完成。

* **SHAKE-256 をデフォルトハッシュに** — SHAKE-256(SHA-3 ファミリー)がデフォルトのアプリケーションハッシュとして採用され、**ML-DSA-87(Dilithium-5)** 署名、**ML-KEM-1024** 鍵カプセル化、**SHAKE-256** ハッシュからなるデフォルトのポスト量子ベースラインが完成しました。

## v3.1.72 — 安定性とメンテナンス

## v1.1.0 — PQC ハイブリッド署名

**リリースの焦点:** ポスト量子暗号セキュリティとアルゴリズムアジリティ。

* **デュアル secp256k1(ECDSA)+ ML-DSA-87 署名** — すべてのトランザクションが古典署名とポスト量子署名の両方を保持し、AnteHandler チェーンで検証されます
* **3つの強制モード** — 設定可能なハイブリッド署名の強制:オフ(モード 0)、許容(モード 1、PQC 任意)、必須(モード 2、PQC 必須)
* **自動登録** — PQC 公開鍵は最初のハイブリッドトランザクション時に自動的に登録され、別途の登録ステップを不要にします
* **SHAKE-256 ハッシュ基盤** — PQC 関連のすべてのハッシュ処理は、量子耐性のあるアドレス導出のために SHAKE-256(SHA-3 ファミリー)を使用します
* **TEE アテステーションインターフェース** — PQC 鍵生成の整合性を証明するための Trusted Execution Environment アテステーションサポート
* **アルゴリズムアジリティフレームワーク** — チェーンアップグレードなしにガバナンスを通じて将来の PQC アルゴリズムを追加できる、プラガブルなアルゴリズムレジストリ
