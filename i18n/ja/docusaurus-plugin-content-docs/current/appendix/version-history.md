# バージョン履歴

QoreChain の公開バージョン履歴です。メインネット **`qorechain-vladi`**(EVM チェーン ID **9801**、2026年6月7日稼働開始)は **v3.2.4** を稼働しています(ガバナンス提案 13 により、2026年10月23日に高さ 3,742,566 で適用。直前のリリースである v3.2.3 は、2026年10月20日に高さ 3,662,051 で適用)。テストネット **`qorechain-diana`**(EVM チェーン ID **9800**)は、高さ 8,337,253(2026年10月19日)以降 **v3.2.4** を稼働しています。

:::note
以下のエントリは高レベルの機能サマリーです。初期の `v1.x` エントリは、メインネット以前のテストネットリリースラインの歴史的記録として保持されています。リリースマニフェスト([メインネットへの接続](/getting-started/connecting-to-mainnet))はタグ付けとは別に公開されるため、タグより遅れる場合があります。新規インストール時に実際に何がダウンロードされるかは、マニフェスト自体を直接確認してください。
:::

## v3.2.4 — ライトノード登録ウィンドウとオプションのタイムロック型ステーキング(メインネット)

**リリースの焦点:** 両ネットワークでの現行リリースです。まずテストネット `qorechain-diana` で稼働しました。テストネットのガバナンス提案 13 により高さ **8,337,253**(2026年10月19日)で適用されました。メインネットでは、ガバナンス提案 13 により2026年10月23日に高さ **3,742,566** で適用されました。ノードはそのブロックまで v3.2.3 のままで、そこで停止して v3.2.4 で再起動し、トランザクションの署名は変わりません。メインネットとテストネットのマニフェストはどちらも `minCompatible` を 3.2.4 に設定しているため、どちらのネットワークに参加するノードにも現在は v3.2.4 が必要です。以下の機能はすべて両ネットワークで稼働しています。

* **ライトノード登録ウィンドウ。** ライトノードの報酬の上限は、直前の決済時点とそのノード自身の登録時点のうち遅い方から始まるため、新規登録のノードが参加前に蓄積された額を受け取ることはありません。
* **オプションのタイムロック型ステーキング(`x/stakingtier`、新規モジュール)。** デリゲーターは、委任の一部を 3、6、または 12 か月間ロックできます。ロックされた部分はアンデリゲートやリデリゲートができず、焼却されるペナルティを支払うことで早期アンロックが可能です。最小ロック額は 10 QOR です。[ステーキングと委任](/user-guide/staking-and-delegation#time-locked-staking)を参照してください。
* **新しい発行モード。** `x/inflation` に3つ目の発行モード `target_apy` が追加され、`target_apy_bps` パラメータ(両ネットワークで `0`。メインネットで適用中のモードは引き続き `fixed`)が加わりました。ネットワークの発行モードの変更は別個のガバナンス上の決定であり、適用中のモードは `/qorechain/inflation/v1/params` で確認できます。
* ポスト量子アカウントレコードに **`possession_proven` フラグ**を追加。アカウント鍵の所有証明は引き続き任意です。
* **ブリッジバリデーターの所有証明。** ブリッジバリデーターの登録には、所有証明と、他のブリッジバリデーターが使用していない鍵が必要です。
* **ブロック時間で数える RDK チャレンジウィンドウ。** オプティミスティックなチャレンジウィンドウは、そこから導出されるブロック数ではなく、ブロック時間で数えられます。
* **ノードローカルなハードニング**(JSON-RPC リクエストの上限、ステートシンクのチャンク予算、鍵登録の事前チェック)と、新しいクエリ(`protocol_features`、`auth_nonce`、および `monthly_cap_active` などライトノード報酬プールの追加フィールド)。

## v3.2.3 — 10月の第2次セキュリティバッチ

**リリースの焦点:** 10月の第2次ハードニングバッチで、メインネットではガバナンス提案 11 により高さ **3,662,051**(2026年10月20日 16:01 UTC)で適用されました。テストネットではそれ以前の高さ 8,003,746(10月15日)で適用済みです。このアップグレードにより、その高さで 52 のプロトコル機能が有効になります。署名形式、アドレス、小数桁数、メモ、手数料は変更されません。

* **ポスト量子鍵の完全性。** 脆弱な鍵、縮退した鍵、すでに使用済みの鍵は登録時に拒否されます。ハイブリッド鍵のメンテナンスが厳格化され、ポスト量子の鍵管理メッセージは authz 経由で実行できなくなり、アカウントは最後の署名アルゴリズムを削除できなくなりました。登録(`MsgRegisterPQCKeyV2`、`tx pqc register-key-v2 ... --pqc-key <name>`)は**任意の所有証明**を受け付け、存在する場合は検証されます。
* **スコープ付き EVM ウィンドウ。** `MsgOpenEVMWindow` は、ウィンドウを絞り込む任意の `native_only`(ネイティブ QOR の単純送金のみ)および `allowed_targets`(最大 16 の宛先)フィールドを受け取ります。[EVM 認可ウィンドウ](/getting-started/first-transaction#evm-window)を参照してください。
* RDK 向けの**ロールアップエスクロー台帳**、プリコンパイルのハードニングを伴う**アトミックなクロス VM キュー**、および**正規のステーク認可**。
* **自己限定のベスティング作成。** ベスティングアカウントの作成は、作成者自身のアカウントにのみ資金を供給できます(3つのベスティングメッセージはサーキットブレーカーでも引き続き停止されています)。
* **経済面の修正。** 発行年はエポック長から導出されるようになり、AMM のエンドブロック処理には上限が設けられ、バーン記録は剪定され、記録されていた滞留ステーカー分はアップグレード高さで 0 から 3,807,496.79 QOR に再計算されました([トークノミクス](/architecture/tokenomics#stranded-and-reserve)を参照)。
* **ライトノードの月次上限。** ノードごとの報酬上限は月単位で表されるようになりました。ノードあたり 30 日で 2,000 QOR で、ブロック時間と稼働率に応じて按分されます。
* **ガバナンスで変更可能なライセンス権限。** 新しい `MsgUpdateAuthority` により、ガバナンスがライセンスを付与する権限者を置き換えられます。
* **公開ビルドは公開ネットワークを拒否。** 公開ソースツリーからビルドされたバイナリは、稼働中のネットワークを指定されると停止します。
* **新しい読み取りルート。** `x/inflation` のパラメータとエポックレコードが、メインネットで REST 経由で提供されます(`/qorechain/inflation/v1/params`、`/epoch_info`)。

## v3.2.2 — 依存関係の更新と10月の第1次セキュリティバッチ(メインネット)

**リリースの焦点:** メインネットではガバナンス提案 7 により高さ **3,556,788**(2026年10月16日 17:59 UTC)で適用された協調アップグレードです。テストネットでは高さ 6,905,034(10月2日)で適用されました。署名形式は変更されません。

* **依存関係。** Cosmos SDK v0.53.8、コンセンサスエンジン v0.38.26、ibc-go v10.7。
* アップグレード高さで **26 のプロトコル機能**が有効になります。主なもの:EIP-7702 の委任にはポスト量子の同意が必要(`MsgAuthorizeEVMDelegation`。`MsgClearEVMDelegation` または `MsgCloseEVMWindow` で解除)、マルチシグの上限がブロック実行で強制される、バリデーターの参加がすべてのパスで検証される、AMM の整合性チェック、モジュールアカウントを EVM 経由で取得できない、EIP-155 以前のトランザクションの拒否、ポスト量子鍵登録が古典鍵を検証する、RDK およびマルチレイヤーのアンカーメッセージが第2の形式(v2)に移行する、失敗トランザクションのバーンチャネルが適用される。

## v3.2.1 — ノードのハードニング

**リリースの焦点:** メインネット向けのノードローカルなセキュリティリリース(2026年10月14日):**アップグレード高さなし、コンセンサス変更なし、ガバナンス投票なし**。v3.2.0 のノードはそのままチェーンに追随し続けます。

* パブリック API のリソース制限を強化し、EVM JSON-RPC とメンプールに上限を設け、昇格された EVM トランザクションをゴシップします。
* EVM チェーン ID をノード設定に固定し、Cosmos チェーン ID と照合します。オペレーターは `app.toml` に `evm-chain-id = 9801` を設定する必要があります(異なる値はエラーとしてログに記録されます)。
* コンセンサスエンジンの依存関係を更新します。システムクロックは NTP で同期した状態に保ってください(60秒を超えるずれでノードが停止します)。
* すべてのオペレーターに推奨します。当時のメインネットマニフェストの `minCompatible` は 3.2.0 でした。

v3.2.1 はノードごとに適用され、アップグレード高さはありません。メインネットでは v3.2.2(10月16日)、v3.2.3(10月20日)、v3.2.4(10月23日)に置き換えられました。

## v3.2.0 — EVM 認可ウィンドウと会計の修正

**リリースの焦点:** ポスト量子要件をすべてのレーンで実効化し、2つの会計上の欠落を解消。メインネットではガバナンス提案 #6 により高さ **2,981,742**(2026年9月25日 12:07 UTC)で適用、テストネットでは高さ 5,920,000 で適用されました。

* **EVM 認可ウィンドウ(EVM ウォレットにとっての破壊的変更)。** EVM トランザクションは、登録済みの ML-DSA-87 鍵を持ち**かつ**ウィンドウが開いているアカウントからのみ受け付けられるようになりました。ウィンドウは Cosmos レーンのメッセージ(`MsgOpenEVMWindow`、ポスト量子署名)で開かれ、ブロック数(≤ 17,280)、トランザクション数(≤ 1,000)、総額(送金額に各トランザクションの最大手数料を加えたもの)で上限が設けられます。`MsgCloseEVMWindow` で失効させます。ウィンドウ内では標準の Ethereum 署名は変更されません。9月16日からサーキットブレーカーによりメインネットで停止されていた EVM レーンは、ルールが発効したのと同じブロックで再開されました。[EVM 認可ウィンドウ](/getting-started/first-transaction#evm-window)を参照してください。
* **ハイブリッド署名 v2。** ポスト量子署名は、ドメインタグ付きでチェーンに紐づく署名対象バイト列に対して行われるようになり、最初の形式はアップグレード高さ以降は拒否されます。クライアントはノードの適用済みアップグレードプランを確認して形式を選択します。CLI(`--sign-bytes auto`)、SDK 0.8.x、wallet-adapter 0.2.x がこれに対応しています。鍵移行およびブリッジアテステーションのペイロードも同じ方式に移行しました。[ポスト量子セキュリティ](/architecture/post-quantum-security#sign-bytes-v2)を参照してください。
* **ステーカー分の支払い。** 手数料分配のうちステーカーの 10 % の取り分は、どの請求権の裏付けにもならない場所に入金されていました。このアップグレード以降は通常のステーキング報酬として支払われます。すでに蓄積された額(メインネットで 6,693,045.92 QOR)はオンチェーンに記録され(`GET /qorechain/burn/v1/stranded_rewards`)、ガバナンス投票(`MsgReleaseStrandedRewards`)によってのみ移動できました。ガバナンスは2026年10月にこれを放出しました([ガバナンスタイムライン](#governance-timeline)および[トークノミクス](/architecture/tokenomics#stranded-and-reserve)を参照)。
* **ライトノード報酬リザーブ。** 適格なノードが存在しない間に蓄積されたライトノードの 3 % の取り分(メインネットで 3,156,009.33 QOR)はリザーブとして記録され(`GET /qorechain/lightnode/v1/reward_pool`)、分配の対象外で、ガバナンスによってのみ移動できます(2026年10月に放出済み)。以降の分配では、前回の実行以降に蓄積された分のみが、ノードごとの上限のもとで支払われます。ライトノードの登録はこのリリース時点ではまだ閉鎖されており、その後開放されました([ライトノード](/light-node/overview#reward-program-status)を参照)。
* **送信者ごとのトランザクション制限**が強制されるようになりました(送信者ごとに 30 ブロックあたり 600 トランザクション。これによりリレイヤーが運用できます)。
* **アップグレードモジュールのバージョンマップ**がすべてのモジュール(48)を列挙するようになり、後続のマイグレーションに影響しかねなかった欠落が修正されました。
* その他:ブリッジのモジュールアカウントとアテステーションペイロードの強化、提案ブロックの検証、ロールアップ決済をロールアップのシーケンサーに限定(ロールアップごとのエスクローと実効的な作成時バーン付き)、マルチレイヤー作成者のステークを登録時にロックし廃止時に返還、スマートアカウントの `enabled` フラグをすべてのパスで強制、バリデーター参加およびベスティング作成のパスを authz のネストから閉鎖。

## v3.1.96 + v3.1.97 — QoreChain Native アクセスのロックダウン

**リリースの焦点:** 業界全体に及ぶ、QoreChain Native が基盤とするランタイムである CosmWasm のセキュリティ勧告を受けて、パーミッションレスなコントラクトコードのアップロードとインスタンス化を封鎖。

* **コントラクトのアップロードとインスタンス化には明示的な許可が必須に。** `code_upload_access` と `instantiate_default_permission` は、メインネットとテストネットの両方で `Nobody` に設定されています——これはオンチェーンパラメータであり、新しいバイナリだけが強制するものではないため、ノードがこの2つのタグのどちらを稼働させているかに関わらず、実際に有効であることを確認済みです。コントラクトを開発している場合にこれが何を意味するかについては、[QoreChain Native 開発](/developer-guide/cosmwasm-development)を参照してください。すでにインスタンス化済みのコントラクトへの影響はなく、`execute` と `query` は従来どおり機能します。両ネットワークとも、QoreChain Native のアップロードおよびインスタンス化の3つのメッセージはサーキットブレーカーでも停止されています。
* 同じ勧告のハードニング指針に従い、**位置独立(PIE)なリリースビルド**を採用しました。これにより、攻撃者がエクスプロイトに必要とするメモリアドレスがプロセスごとにランダム化されます。動的リンクバイナリではビルドフラグを1つ追加するだけで済み、状態を壊さないことを確認済みです。

## v3.1.95 — Cosmos EVM ハードニング

**リリースの焦点:** EVM 残高会計ライブラリに対するローリングセキュリティアップデート。

* **オーバーフロー対策の強化** — EVM の残高更新パスは、極端なオーバーフロー条件下で黙ってラップアラウンドするのではなく、安全に失敗するようになりました。コンセンサスを壊さないローリングアップデートとして提供され、ガバナンス投票や協調ハルト高さは不要でした。

## v3.1.94 — 発行上限と管理系メッセージのハードニング

**リリースの焦点:** ステーキング報酬の発行量を実際のネットワーク状況に合わせ、権限付き管理系メッセージの認可チェックを強化。

* **発行上限** — 完全なボンド済みステークの支持を得て可決されたガバナンス提案が、高さ 2,122,074(2026年8月26日)で適用され、元の逓減型発行スケジュールを、確定した累積上限のもとでのエポックごとの固定額に置き換えました。元のスケジュールは、はるかに成熟した完全ボンド状態のネットワークを想定して調整されていたため、実際のボンド済みステークに対しては想定よりはるかに速いペースで支払われていました。エポックごとの額と上限は、2026年10月19日にガバナンス提案 10 によって引き上げられました。現在の数値については[トークノミクス](/architecture/tokenomics#staking-reward-schedule)を参照してください。
* **管理系メッセージのハードニング** — 権限付き・認可ゲート付きの一連の管理系メッセージについて、署名者の検証が、メッセージ自体に含まれる値を信頼するのではなく、ガバナンスモジュール自身のアドレスと照合して行われるようになりました。
* このリリースへ直接アップデートするノードのために、v3.1.92 のノードオンボーディング信頼性の修正も引き続き含まれています。

## v3.1.92 — ノード同期の信頼性向上

**リリースの焦点:** スナップショットおよび公開チェーンアーカイブからのノードオンボーディングの信頼性向上。

* **スナップショット/アーカイブ同期の修正** — ステートシンクのスナップショットまたは公開チェーンアーカイブから復元するノードが、特定の過去のブロックを超えて同期を完了できなくなる問題を解消しました。いずれの経路によるオンボーディングも確実に完了するようになりました。

## v3.1.90 — ライトノード稼働率の集計

**リリースの焦点:** ライトノードの報酬適格性のために計測される稼働率が、時間経過にわたって一貫して積算されるようになりました。

* **前方積算される稼働率** — ライトノードの報酬適格性の稼働率は、現在有効なハートビート間隔を使ってその全履歴を再計算するのではなく、そのノード自身の登録時点から、各時点で有効だったハートビート間隔に基づいて期待されるハートビート数を前方に積算することで算出されるようになりました。したがって、ハートビート間隔へのガバナンス変更は今後の稼働率にのみ影響し、ノードの過去の実績を遡って再評価することはありません。

## v3.1.86 — バリデーター復旧のセーフガード

**リリースの焦点:** バリデーターがダウンタイムジェイルからの復旧に永続的に失敗する状態を防止。

* **ジェイルロックの修正** — ポスト量子鍵を未登録のバリデーターオペレーターアカウントは、ハイブリッド署名の強制が「必須(古典署名フォールバック無効)」に設定されている場合でも、ダウンタイムジェイルからの復旧のために常に `MsgUnjail` を送信できるようになりました。以前は、ジェイル解除自体に送信をブロックされているトランザクションの送信が必要だったため、そのようなアカウントには復旧手段がありませんでした。
* **ステートシンクスナップショット** — スナップショット生成がネットワーク全体で有効化され、新規バリデーターおよびフルノードが完全な過去のリプレイではなくステートシンクによって高速に参加できるようになりました。

## v3.1.85 — 連携ウォレットによる委任支出

**リリースの焦点:** 連携された外部ウォレット鍵(Phantom、MetaMask)が、最小権限の許可・支出上限・即時失効のもとで、単一の正規のポスト量子アカウントから**支出**できるようになりました。

* **オーセンティケーター実行レーン** — 2つの新しいメッセージにより、登録済みのオーセンティケーターが、アカウント所有者が不在でも正規アカウントからの送金を許可できるようになりました。**`MsgExecuteEVM`**(アカウントの `0x…` アドレスからの EVM コール/送金)と **`MsgExecuteCosmos`**(Native レーンでのバンク送金)です。**リレイヤー**がエンベロープを送信・手数料負担します(リレイヤー自身のハイブリッド PQC 署名がトランザクション要件を満たします)。一方、ドメイン分離されリプレイに紐づいた署名対象バイト列に対するオーセンティケーターの署名が認可となります。外部鍵に ML-DSA による共同署名は一切不要です。
* **オーセンティケーターとしての MetaMask** — secp256k1 オーセンティケーターは、33バイトの圧縮鍵形式に加えて、**20バイトの Ethereum アドレス**として登録し、**EIP-191 `personal_sign`** で検証できるようになりました。これにより、標準的な MetaMask アカウントを連携させ、上限の範囲内で支出させることができます。
* **3レーンすべてでの権限強制** — 許可スコープと **SpendingRule** による金額上限(トランザクションごと・日次上限)は、Native、EVM、SVM の各レーンで強制され、鍵管理系メッセージは決して委任できません。個別のエラーコードにより、ウォレット側で適切なメッセージを表示できます:`5` 支出上限超過、`6` オーセンティケーター期限切れ、`10` 権限拒否、`11` リプレイ拒否。
* **権限スキーマクエリ** — `GET /qorechain/abstractaccount/v1/permission_schema`(gRPC/CLI でも利用可)は、正規の権限タクソノミー(11 種類の権限)、メッセージから権限へのマッピング、および委任不可メッセージの一覧を返すため、ウォレットはスコープをハードコードせずに検証できます。
* **同一アルゴリズムでの PQC 鍵ローテーション** — 新しい **`MsgRotatePQCKey`** は、アカウントの ML-DSA-87 鍵を同一アルゴリズム内でローテーションします(旧鍵と新鍵の両方による二重署名)。これにより、レガシー方式で導出された鍵を正規のアドレス紐づけ導出方式へ移行させたり、漏えいした鍵を失効させたりできます。新しい CLI:`tx pqc rotate-key` および `tx pqc recover-key`(ニーモニックからの決定論的な鍵復元)。
* **ルート鍵トランザクションへの影響なし** — 今回の変更は加算的なもので、通常のウォレットおよび取引所のフローは変わりません。ノードオペレーターは、ネットワークアップグレードの高さまでに **v3.1.85** に移行する必要があります。
* **現在の状況** — スマートアカウントと連携ウォレットの機能は実装済みですが、現在は両ネットワークで**無効化**されています(`abstractaccount.enabled = false`)。v3.2.0 以降、このフラグが無効の間はすべてのオーセンティケーターのパスが拒否されます。連携フローを提供する前に `GET /qorechain/abstractaccount/v1/config` を確認してください。

## v3.1.84 — オーセンティケーター権限と支出上限

**リリースの焦点:** 委任支出の背後にある権限モデル。

* **正規の権限タクソノミー** — 11 種類の権限(`all`、`send`、`delegate`、`withdraw`、`vote`、`evm`、`wasm`、`svm`、`amm`、`ibc`、`deploy`)と、フェイルクローズなメッセージ→権限マッピング:マッピングされていないメッセージタイプは拒否され、鍵管理系メッセージは決して委任できません。
* **SpendingRule の強制** — 許可デノム一覧付きの、トランザクションごと・日次(UTC)の支出上限が強制され、(アカウント, オーセンティケーター)のペアごとに記録されます。
* **SVM レーンの認可** — 外部方式の鍵(例:Phantom の ed25519)によって SVM レーンで認可されるアクションも、同じ中央認可ゲートを経由します。

## v3.1.83 — 3つのインターフェース全体での統一アカウント署名

**リリースの焦点:** 1つの鍵、1つのアカウント — Cosmos、EVM、SVM の各インターフェースで、残高を保持するだけでなく**署名**もできる、単一の統一アイデンティティ。

* **すべてのレーンで1つの鍵が署名** — eth-native 方式(アドレス = secp256k1 公開鍵の keccak)で作成されたアカウントは、EVM トランザクションに加えて、`eth_secp256k1` 方式で Cosmos レーンのトランザクションにも署名できるようになりました。その `qor1…`(Cosmos)、`0x…`(EVM)、Solana-VM(base58)形式は、1つの残高を**保持**し、3レーンすべてで**支出**できる(ポスト量子ハイブリッド〔ML-DSA-87〕による Cosmos トランザクションを含む)単一の20バイトのアイデンティティです。
* **ポスト量子署名は変更なし** — 統一アカウントは引き続き ML-DSA-87 鍵を登録し、チェーンが要求する FIPS-204 ハイブリッド署名を保持します。古典署名部分はコインタイプ118方式ではなく `eth_secp256k1`(keccak)になります。既存のコインタイプ118アカウントには影響しません。
* **コンセンサスに中立なローリングアップグレード** — 両ネットワークでバイナリのローリングアップグレードとして提供され、**再ジェネシスもチェーン停止もありません**。アカウント残高、履歴、ジェネシスは変更されません。
* **クライアントツール** — `@qorechain/wallet-adapter` 0.1.5 は eth-native な Cosmos 署名(`signClassicalEth` / `signHybridEth`)、統一された3アドレス生成、および `walletFromSeed`(任意の32バイトシード — 例:Phantom の署名 — から正規アカウントを導出)を追加します。`@qorechain/chain-bridge` は `eth_secp256k1` 署名パスを獲得します。

:::caution ノードオペレーター — アップグレード必須
フルノードは **v3.1.83 以降**で稼働する必要があります。v3.1.83 より前のノードは eth-native(`eth_secp256k1`)トランザクションをデコードできず、そのようなトランザクションがブロックに現れると同期が止まります。[download.qore.host](https://download.qore.host) から現行バンドルをダウンロードしてください。
:::

## v3.1.81 — SVM ネイティブ QOR 統合

**リリースの焦点:** Solana 互換インターフェース上でのファーストクラス資産としてのネイティブ QOR。

## v1.1.0 — PQC ハイブリッド署名

**リリースの焦点:** ポスト量子暗号セキュリティとアルゴリズムアジリティ。

* **デュアル secp256k1(ECDSA)+ ML-DSA-87 署名** — すべてのトランザクションが古典署名とポスト量子署名の両方を保持し、AnteHandler チェーンで検証されます
* **3つの強制モード** — 設定可能なハイブリッド署名の強制:オフ(モード 0)、許容(モード 1、PQC 任意)、必須(モード 2、PQC 必須)
* **鍵の登録** — 初期のビルドでは最初のハイブリッドトランザクション時に PQC 公開鍵が自動登録されていましたが、その動作は削除され、現在は `MsgRegisterPQCKey` で明示的に鍵を登録します([はじめてのトランザクション](/getting-started/first-transaction#register-pqc-key)を参照)
* **SHAKE-256 ハッシュ基盤** — PQC 関連のすべてのハッシュ処理は、量子耐性のあるアドレス導出のために SHAKE-256(SHA-3 ファミリー)を使用します
* **TEE アテステーションインターフェース** — PQC 鍵生成の整合性を証明するための Trusted Execution Environment アテステーションサポート
* **アルゴリズムアジリティフレームワーク** — チェーンアップグレードなしにガバナンスを通じて将来の PQC アルゴリズムを追加できる、プラガブルなアルゴリズムレジストリ

## v1.0.0 — ジェネシス(トークノミクスエンジン)

**リリースの焦点:** フルトークノミクス、マルチ VM 実行、AI 支援運用を備えた初期プロトコルローンチ。

* **x/burn モジュール** — バリデーター、バーン、トレジャリー、ステーカーへの4分割分配を伴う、マルチチャネル手数料バーンメカニズム
* **x/xqore モジュール** — 段階的な早期アンロックペナルティと PvP リベース再分配を備えたガバナンスステーキングデリバティブ
* **x/inflation モジュール** — 年次減衰を伴うエポックベースの発行(v3.1.94 で、確定した累積上限のもとでのエポックごとの固定額に置き換えられました)
* **PRISM コンセンサスレイヤー** — 動的なチェーンパラメータチューニングのための強化学習最適化(PPO)(サーキットブレーカーによる安全制御を含む)
* **トリプルプール CPoS** — レピュテーションスコアで重み付けされた RPoS、DPoS、PoS のバリデータープールによる Composite Proof-of-Stake(`x/qca` に実装済み。ブロック生成にはまだ接続されていません)
* **QDRW ガバナンス** — Quadratic Delegation with Reputation Weighting による投票権計算式(実装済み。稼働中のネットワークでは無効)
* **EVM + QoreChain Native + SVM ランタイム** — QoreChain EVM Engine、QoreChain Native スマートコントラクト、Solana Virtual Machine という3つの同時実行環境
* **クロス VM ブリッジ** — 単一ブロック内での EVM、QoreChain Native、SVM ランタイム間のメッセージパッシングと資産移転
* **ポスト量子暗号** — 高性能な PQC ライブラリに支えられた量子耐性のある署名
* **QCAI** — 不正検知、手数料推定、ネットワーク最適化のための、オプションのオフチェーンサイドカーを伴うオンチェーンヒューリスティック分析
* **コンテナ化デプロイ** — サイドカーサービスとブロックインデクサーを備えたフルマルチバリデーターテストネットデプロイ
* **ブロックインデクサー** — 過去のクエリと分析のための永続ストレージを備えたブロックリスナー
