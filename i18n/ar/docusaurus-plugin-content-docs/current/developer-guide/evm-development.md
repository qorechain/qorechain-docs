# تطوير EVM

تُشغّل QoreChain بيئة تنفيذ متوافقة بالكامل مع EVM على محرك QoreChain EVM Engine، مما يتيح لك نشر عقود Solidity الذكية والتفاعل معها باستخدام الأدوات المألوفة. تعرض وحدة EVM واجهة JSON-RPC على **المنفذ 8545** (وWebSocket على **8546**) تدعم سير عمل تطوير Ethereum القياسي.

:::note
تستهدف الأمثلة أدناه شبكة **`qorechain-vladi`** الرئيسية (معرّف سلسلة EVM **9801**)، العاملة منذ 7 يونيو 2026، والتي تشغّل وقت كتابة هذا إصدار العقدة **v3.2.6** (طُبّق بمقترح الحوكمة 15 عند الارتفاع 4,020,000 في 4 نوفمبر 2026؛ وكان v3.2.5 قد طُبّق عند الارتفاع 3,906,833 في 29 أكتوبر 2026 وكان v3.2.4 قد طُبّق عند الارتفاع 3,742,566 في 23 أكتوبر 2026 وv3.2.3 عند الارتفاع 3,662,051 في 20 أكتوبر 2026). أما شبكة الاختبار **`qorechain-diana`** فتعمل بالإصدار **v3.2.8** منذ 12 نوفمبر 2026 (v3.2.4 منذ الارتفاع 8,337,253 في 19 أكتوبر 2026، وv3.2.5 عند الارتفاع 8,890,800 في 26 أكتوبر، وv3.2.6 عند الارتفاع 8,970,638 في 27 أكتوبر، وv3.2.7 عند الارتفاع 9,594,600 في 6 نوفمبر، وv3.2.8 عند الارتفاع 9,929,500 في 12 نوفمبر)؛ استخدم هناك معرّف سلسلة EVM **9800**. وحيثما تصف هذه الصفحة شيئًا يختلف بين الشبكتين (الإضافات المدمجة في شبكة الاختبار، ورموز Fest التجريبية) فإنها توضّح ذلك. تستخدم الأمثلة البرمجية العنوان `http://localhost:8545` لعقدة تشغّلها بنفسك؛ ونقطة النهاية العامة للشبكة الرئيسية هي `https://evm.qore.host` ونقطة نهاية شبكة الاختبار هي `https://evm-testnet.qore.host`.
:::

:::caution تحتاج معاملة EVM إلى مفتاح PQC مسجَّل ونافذة تفويض مفتوحة
منذ ترقية v3.2.0 (الشبكة الرئيسية عند الارتفاع 2,981,742، وشبكة الاختبار عند الارتفاع 5,920,000) لا يقبل مسار EVM معاملة إلا من حساب لديه **(1) مفتاح ML-DSA-87 لاحق للكم مسجَّل** و**(2) نافذة تفويض EVM مفتوحة** ما زال فيها متسع لها. أنت توقّع بالأدوات المعتادة (MetaMask وethers.js وHardhat وFoundry)، لكن من دون مفتاح مسجَّل ونافذة مفتوحة يُرفض `eth_sendRawTransaction` (النطاق `pqc`، الرموز 26 أو 27 أو 28). أما القراءات و`eth_call` وتقدير الغاز فلا تحتاج إلى أي منهما. راجع [نافذة تفويض EVM](#evm-window) أدناه والدليل التفصيلي خطوة بخطوة في [معاملتك الأولى](/getting-started/first-transaction#evm-window).

تنطبق قاعدتان أخريان على الشبكة الرئيسية منذ v3.2.2: **تُرفض المعاملات غير المحمية (ما قبل EIP-155)**، سواء في mempool العقدة أو أثناء تنفيذ الكتل، لذا وقّع مع معرّف سلسلة (وهذا ما تفعله كل محفظة ومكتبة حالية)؛ و**لا يمكن الاستيلاء على حسابات الوحدات (module accounts) عبر EVM**.
:::

## نقطة نهاية JSON-RPC

| الخاصية               | القيمة                                      |
| --------------------- | ------------------------------------------ |
| عنوان URL الافتراضي   | `http://localhost:8545`                    |
| عنوان URL لـ WebSocket | `ws://localhost:8546`                      |
| المساحات المدعومة     | `eth_`, `web3_`, `net_`, `txpool_`          |
| معرّف السلسلة (الشبكة الرئيسية) | `9801` (`qorechain-vladi`)       |
| معرّف السلسلة (شبكة الاختبار)   | `9800` (`qorechain-diana`)       |
| رمز العملة            | `QOR`                                      |

تُخدَّم القراءات الخاصة بـ QoreChain عبر REST (`api.qore.host`)؛ أما مساحة `qor_` في JSON-RPC الموصوفة [أدناه](#custom-qor_-namespace) فهي **غير مفعّلة** على نقاط النهاية العامة ولا في إعدادات العقدة الافتراضية. قائمة `api` الافتراضية لعقدة مُهيَّأة حديثاً (v3.2.3 وما بعده) هي `eth,net,web3`؛ أما `txpool` فاختياري التفعيل، لأنه ينشر المعاملات المعلّقة في العقدة.

ابتداءً من إصدار العقدة v3.2.4 (على الشبكة الرئيسية منذ 23 أكتوبر 2026، وعلى شبكة الاختبار منذ 19 أكتوبر 2026) تضع العقدة حدودًا لخادم JSON-RPC الخاص بها: تُرفض أجسام الطلبات التي تتجاوز 256 KiB (HTTP 413)، ولا يُخدَّم أكثر من 256 طلبًا في آن واحد (HTTP 503 فيما يزيد على ذلك)، ويُرفض مرشِّح `eth_getLogs` أو `eth_newFilter` الذي يضم أكثر من 4 مواضع للمواضيع (topics)، أو 1000 بديل في موضع واحد، أو 1000 عنوان. هذه الحدود إعدادات محلية للعقدة في قسم `[json-rpc]` من `app.toml`؛ راجع [تشغيل عقدة](/developer-guide/running-a-node#exposing-endpoints-for-integration).

## Hardhat

ثبّت Hardhat وقم بإعداد ملف `hardhat.config.js` الخاص بك:

```javascript
require("@nomicfoundation/hardhat-toolbox");

module.exports = {
  solidity: "0.8.24",
  networks: {
    qorechain: {
      url: "http://localhost:8545",
      accounts: ["0xYOUR_PRIVATE_KEY_HEX"],
      chainId: 9801, // mainnet qorechain-vladi (use 9800 for qorechain-diana testnet)
    },
  },
};
```

انشر عقداً (يحتاج الحساب الذي يجري النشر إلى مفتاح PQC مسجَّل و[نافذة تفويض](#evm-window) مفتوحة؛ ويُحتسب النشر معاملة EVM واحدة ضمن النافذة):

```bash
npx hardhat run scripts/deploy.js --network qorechain
```

تشغيل الاختبارات على EVM الخاص بـ QoreChain:

```bash
npx hardhat test --network qorechain
```

## Ethers.js

```javascript
import { ethers } from "ethers";

// Connect to QoreChain EVM
const provider = new ethers.JsonRpcProvider("http://localhost:8545");

// Get chain info
const network = await provider.getNetwork();
console.log("Chain ID:", network.chainId); // 9801n on mainnet (9800n on testnet)

// Read balance
const balance = await provider.getBalance("0xYourAddress");
console.log("Balance:", ethers.formatEther(balance), "QOR");

// Send transaction
const wallet = new ethers.Wallet("0xYOUR_PRIVATE_KEY_HEX", provider);
const tx = await wallet.sendTransaction({
  to: "0xRecipientAddress",
  value: ethers.parseEther("1.0"),
});
await tx.wait();
```

## نموذج الغاز

تستخدم QoreChain نموذج **رسوم أساسية ديناميكية وفق EIP-1559** لمعاملات EVM:

* تُضبط الرسوم الأساسية لكل كتلة بناءً على مستوى الاستخدام
* يمكن للمستخدمين ضبط `maxFeePerGas` و`maxPriorityFeePerGas`
* تذهب رسوم الأولوية إلى مقترح الكتلة

### حدود الغاز {#gas-limits}

منذ الإصدار v3.2.8 (على شبكة الاختبار فقط إلى حين ترقية لاحقة للشبكة الرئيسية) يجوز لمعاملة EVM الواحدة أن تضبط حد غاز لا يزيد على **30,000,000**، وتتشارك عمليات EVM التي تبدأها رسالة Cosmos واحدة (استدعاء cross-VM أو تحويل ERC-20 أو نقل حزمة IBC واردة) الميزانية نفسها. وتُرفض المعاملة التي تتجاوز الحد قبل تنفيذها. اقرأ القيم السارية من `GET /qorechain/pqc/v1/evm_limits` (gRPC `EVMLimitsQuery/EVMLimits`) وقيّد الغاز الذي ترسله أدواتك، خصوصاً الغاز الذي يمرّره dApp إلى محفظتك دون فحص. ولمعاملة Cosmos حدها الخاص البالغ 50,000,000 غاز. أما التحويلات البسيطة (21,000 غاز) واستدعاءات الرموز العادية فهي أقل بكثير من الحدّين.

### جسر الفئات العددية

يمتلك رمز QOR الأصلي **6 خانات عشرية** (`uqor`)، بينما يتوقّع EVM **18 خانة عشرية**. تتولّى وحدة `x/precisebank` عملية التحويل السلسة:

| السياق          | الفئة العددية | الخانات العشرية | مثال                    |
| ---------------- | -------------- | ---------------- | ------------------------ |
| السلسلة الأصلية  | `uqor`         | 6                | `1000000 uqor = 1 QOR`  |
| EVM              | wei            | 18               | `1e18 wei = 1 QOR`      |

هذا التحويل شفاف — فعندما تتحقّق من رصيد عبر `eth_getBalance`، تكون الاستجابة مقوّمة بوحدة wei ذات 18 خانة عشرية. وعندما يُستعلم عن الحساب نفسه عبر وحدة البنك الأصلية، يظهر الرصيد بوحدة `uqor` ذات 6 خانات عشرية.

## أزواج رموز ERC-20 {#erc20-token-pairs}

توفّر وحدة `x/erc20` **أزواج رموز** بين الفئات العددية الأصلية في Cosmos SDK وعقود ERC-20:

* يمكن استخدام الرموز الأصلية داخل عقود EVM كرموز ERC-20
* يمكن تحويل رموز ERC-20 المنشورة على EVM إلى فئات عددية أصلية
* التحويل ثنائي الاتجاه ويُدار على مستوى البروتوكول

```bash
# Register a native ERC-20 contract as a token pair (permissioned: `permissionless_registration` is false)
qorechaind tx erc20 register-erc20 <contract-addr> --from mykey

# Convert native tokens to ERC-20
qorechaind tx erc20 convert-coin 1000000uqor --from mykey --gas 400000 --fees 40000uqor

# Convert ERC-20 back to native
qorechaind tx erc20 convert-erc20 <contract-addr> 1000000000000000000 --from mykey --gas 400000 --fees 40000uqor
```

هذه معاملات في مسار Cosmos: وعلى الشبكات الفعلية تحتاج أيضاً إلى التوقيع المشترك الهجين ما بعد الكمومي (ابنِها باستخدام `--generate-only`، ثم `qorechaind tx pqc cosign`؛ راجع [التوقيع ما بعد الكمومي](/developer-guide/post-quantum-signing)). يُرفض أمر `convert-erc20` العادي أعلاه في إصدار العقدة v3.2.6 لأن CLI يكتب مُرسِلًا بصيغة `0x`؛ راجع [التحويل بين الشكلين](#fest-convert) للصيغة العاملة. تُسجَّل أزواج الرموز بموجب سياسة مقيَّدة بالأذونات (تسجّلها الحوكمة). ولا يوجد أي زوج منها على الشبكة الرئيسية وقت كتابة هذا؛ وعلى شبكة الاختبار رموز Fest التجريبية في [القسم التالي](#fest-tokens).

## رموز Fest التجريبية وتحويل ERC20 {#fest-tokens}

:::note لشبكة الاختبار فقط، بلا قيمة
الرموز في هذا القسم موجودة فقط على شبكة الاختبار `qorechain-diana` (معرّف سلسلة EVM 9800). وهي رموز اختبار للمطوّرين ولا قيمة لها. وليس في الشبكة الرئيسية أي زوج رموز ERC-20 (جرى التحقق في 27 أكتوبر 2026)، لذا لا توجد هناك أي من الفئات أدناه.
:::

في 27 أكتوبر 2026 سجّلت حوكمة شبكة الاختبار (المقترح 26) ثلاثة عقود ERC-20 بوصفها أزواج رموز. وهي تمنح المطوّرين رمزًا ثانيًا للإقران مع QOR في [مجمّع AMM](/api-reference/rest-grpc-endpoints#amm-module):

| الرمز | عقد ERC-20 (EIP-55) | الخانات العشرية | الفئة المصرفية |
| ----- | ------------------- | --------------- | -------------- |
| fUSD (FestUSD) | `0x97143B771D34ddb9130b807b135Ae675A5a963CA` | 6  | `erc20:0x97143B771D34ddb9130b807b135Ae675A5a963CA` |
| fETH (FestETH) | `0x02292293c13880a26242690eb70a0e42B8E91c28` | 18 | `erc20:0x02292293c13880a26242690eb70a0e42B8E91c28` |
| fBTC (FestBTC) | `0x4604e7E45b2ecdbfbDc157103f5B2b62cb16451A` | 8  | `erc20:0x4604e7E45b2ecdbfbDc157103f5B2b62cb16451A` |

* **الفئة المصرفية هي `erc20:<address>` بنقطتين رأسيتين، ويجب أن يكون العنوان بصيغة EIP-55 المختلطة الحالة تمامًا كما هو معروض.** الفئات حساسة لحالة الأحرف: فـ `erc20:0x97143b771d34...` (بأحرف صغيرة) سلسلة مختلفة، ويردّ الاستعلام عنها بـ `404`. انسخ الفئة من `GET https://api-testnet.qore.host/cosmos/bank/v1beta1/denoms_metadata`، الذي يسرد الرموز الثلاثة مع `symbol` (`fUSD` و`fETH` و`fBTC`) واسم العرض `display` (`FestUSD` و`FestETH` و`FestBTC`) والخانات العشرية.
* **يدفع الصنبور عملات مصرفية.** لاستخدام رمز Fest من EVM ‏(MetaMask وSolidity)، حوّل العملة المصرفية أولًا إلى شكل ERC-20 عبر `MsgConvertCoin`؛ ولإعادة رصيد ERC-20 إلى الشكل المصرفي (مثلًا لإقرانه في AMM) استخدم `MsgConvertERC20`. وكلاهما موصوف فيما يلي.
* **توجد الرموز بشكلين.** يُقرأ رصيد ERC-20 بالدالة `balanceOf` في العقد عبر JSON-RPC الخاص بـ EVM؛ أما الرصيد المحوَّل فهو عملة مصرفية تُقرأ بـ `GET /cosmos/bank/v1beta1/balances/{address}`. ولا يمكن إقران سوى شكل العملة المصرفية في AMM. والتحويل ينقل القيمة بين الشكلين؛ ولا ينشئها.
* **تستخدم المبالغ الخانات العشرية الخاصة بالرمز** (6 و18 و8 لـ fUSD وfETH وfBTC)، لا الخانات العشرية الست الخاصة بـ `uqor`.

```bash
curl -s https://api-testnet.qore.host/cosmos/evm/erc20/v1/token_pairs
curl -s "https://api-testnet.qore.host/cosmos/evm/erc20/v1/token_pairs/0x97143B771D34ddb9130b807b135Ae675A5a963CA"
```

### التحويل بين الشكلين {#fest-convert}

رسالتا التحويل كلتاهما معاملتان في مسار Cosmos: تحتاجان إلى مفتاحك المسجَّل لما بعد الكم والتوقيع المشترك الهجين، كأي معاملة أصلية أخرى (ابنِها، ثم `qorechaind tx pqc cosign`؛ راجع [التوقيع ما بعد الكمومي](/developer-guide/post-quantum-signing)). يجب ألا تقل الرسوم عن gas × 0.1 uqor.

:::note ما الذي جرى تشغيله
جرى تشغيل قراءات REST في هذه الصفحة (`token_pairs` و`denoms_metadata`) على شبكة الاختبار في 27 أكتوبر 2026. أما أمرا التحويل أدناه فلم **يُشغَّلا** من البداية إلى النهاية لأجل هذه الصفحة: فأشكال الرسائل وقاعدة المُرسِل مأخوذة من شيفرة العقدة v3.2.6 ومن مرجع فريق السلسلة. تعامل معهما بوصفهما الشكل الموثَّق، وتأكد بمبلغ صغير أولًا.
:::

**من عملة مصرفية إلى ERC-20: ‏`MsgConvertCoin`.** الحقل `coin` هو الفئة المصرفية الدقيقة الحساسة لحالة الأحرف (`erc20:<EIP-55 address>`)، و`sender` هو عنوانك `qor1...` (الموقِّع)، و`receiver` هو عنوان `0x...` الذي سيحتفظ بـ ERC-20. يستهلك نحو 432,000 غاز؛ اضبط حد غاز قدره 600,000.

```bash
# Write the message by hand (not run for this page)
cat > convert-coin.json <<'JSON'
{
  "body": {
    "messages": [{
      "@type": "/cosmos.evm.erc20.v1.MsgConvertCoin",
      "coin": { "denom": "erc20:0x97143B771D34ddb9130b807b135Ae675A5a963CA", "amount": "1000000" },
      "receiver": "0xYOUR_EVM_ADDRESS",
      "sender": "qor1youraddr..."
    }],
    "memo": ""
  },
  "auth_info": { "signer_infos": [], "fee": { "amount": [{ "denom": "uqor", "amount": "60000" }], "gas_limit": "600000" } },
  "signatures": []
}
JSON
qorechaind tx pqc cosign convert-coin.json --from mykey --pqc-key mypqc --chain-id qorechain-diana
```

**من ERC-20 إلى عملة مصرفية: ‏`MsgConvertERC20`.** يجب أن يكون حقل `sender` فيها أيضًا عنوان bech32 `qor1...` للحساب. ويُرفض مُرسِل بصيغة `0x` بالخطأ `decoding bech32 failed`. وفي إصدار العقدة v3.2.6 (الشبكة الرئيسية اليوم) يكتب أمر CLI ‏`qorechaind tx erc20 convert-erc20` (المثال العادي في [أزواج رموز ERC-20](#erc20-token-pairs)) المُرسِل بصيغة `0x`، فيُرفض لهذا السبب: لا تستخدمه هناك. ومن v3.2.7 (على شبكة الاختبار منذ 6 نوفمبر 2026، وليس على الشبكة الرئيسية بعد) يكتب الأمر المُرسِل بصيغة `qor1`. وفي أي من الإصدارين يمكنك بناء الرسالة بنفسك بعنوان `qor1` مُرسِلًا، بالطريقة نفسها كما أعلاه:

```bash
# Workaround: write the message with a qor1 sender (not run for this page)
cat > convert-erc20.json <<'JSON'
{
  "body": {
    "messages": [{
      "@type": "/cosmos.evm.erc20.v1.MsgConvertERC20",
      "contract_address": "0x97143B771D34ddb9130b807b135Ae675A5a963CA",
      "amount": "1000000",
      "receiver": "qor1youraddr...",
      "sender": "qor1youraddr..."
    }],
    "memo": ""
  },
  "auth_info": { "signer_infos": [], "fee": { "amount": [{ "denom": "uqor", "amount": "60000" }], "gas_limit": "600000" } },
  "signatures": []
}
JSON
qorechaind tx pqc cosign convert-erc20.json --from mykey --pqc-key mypqc --chain-id qorechain-diana
```

هنا `receiver` هو حساب `qor1...` الذي يتلقى العملة المصرفية (تقبل الوحدة صيغة bech32 للمستلِم في التحويل إلى عملة مصرفية). المبلغ بالوحدات الأساسية للرمز (6 أو 18 أو 8 خانات عشرية). انسخ الفئة لـ `MsgConvertCoin` من `denoms_metadata` فقط؛ فالصيغة ذات الأحرف الصغيرة تُرفض بالخطأ `token pair not found`.

## توافق PQC وEVM

تُوقَّع معاملات EVM باستخدام **ECDSA الكلاسيكي (secp256k1)**، ولذلك تبنيها وتوقّعها أدوات MetaMask وHardhat وFoundry وethers.js وغيرها من الأدوات القياسية دون أي تعديل. ما تغيّر في **v3.2.0** هو *القبول*: لا تُقبل المعاملة إلا إذا كان لدى مرسلها مفتاح ما بعد كمومي مسجَّل ونافذة تفويض سارية (القسم التالي). تسجيل المفتاح وفتح النافذة هما معاملتان في مسار Cosmos وتتطلبان التوقيع الهجين (ML-DSA-87 + secp256k1).

للأمان ما بعد الكمومي داخل العقود:

* تتحقق **إضافة PQC Verify المدمجة** (`0x0000...0A01`) من توقيعات ML-DSA-87 على السلسلة من Solidity. وهي **مفعّلة على شبكة الاختبار** (فعّلها مقترح الحوكمة 21، الذي أُقرّ في 27 أكتوبر 2026) و**غير مفعّلة على الشبكة الرئيسية** وقت كتابة هذا. راجع [إضافات EVM المدمجة: حالة الشبكة](/developer-guide/evm-precompiles#network-status).
* **الرسائل عبر الآلات الافتراضية** من EVM إلى QoreChain Native أو SVM هي معاملات في مسار Cosmos وتحمل التوقيع الهجين كأي معاملة أخرى؛ راجع [التشغيل البيني عبر الآلات الافتراضية](/developer-guide/cross-vm-interoperability) لمعرفة توافرها الحالي.

ومن إصدار العقدة v3.2.7 (على شبكة الاختبار منذ 6 نوفمبر 2026، وليس على الشبكة الرئيسية بعد) تصبح `eth_getBlockByNumber` و`eth_getBlockReceipts` و`eth_feeHistory` أكثر موثوقية، وكذلك للكتل التي تحتوي معاملة EVM فاشلة. وفي 7 نوفمبر 2026 ردّت الطرق الثلاث بشكل طبيعي على نقطة النهاية العامة لشبكة الاختبار.

## نافذة تفويض EVM {#evm-window}

**نوع المفتاح.** لا يعمل مسار EVM والنافذة إلا بمفتاح `eth_secp256k1`، وهو نوع مفتاح إيثريوم (نوع العملة 60). أما مفتاح Cosmos القياسي من نوع secp256k1 (نوع العملة 118، وهو حساب `qor1…` الافتراضي في QoreX) فلا يستطيع التوقيع لعنوان EVM الخاص به، ولذلك فإن النافذة المفتوحة على حساب كهذا لا تحقق شيئًا. في QoreX استخدم **إضافة حساب إيثريوم (العملة 60)** ضمن حساباتك؛ راجع [استعادة عبارة من MetaMask أو لوحة التحكم](/qorex/getting-started#restore-dashboard).

ومن v3.2.7 (على شبكة الاختبار منذ 6 نوفمبر 2026، وليس على الشبكة الرئيسية بعد) تُصدر معاملة EVM التي تستهلك النافذة الحدث `pqc_evm_window_used`، مع السمة `source` التي تبيّن أي مسار استخدمها.

لا يمكن للتوقيع ما بعد الكمومي أن يسافر *مع* معاملة Ethereum (فالمحافظ مثل MetaMask لا تستطيع إرفاق توقيع ثانٍ)، لذلك يسافر *قبلها*. يفتح الحساب نافذة محدودة بالرسالة `MsgOpenEVMWindow` في مسار Cosmos؛ ثم لا يقبل مسار EVM إلا المعاملات التي تغطيها نافذة سارية. المفتاح الكلاسيكي المسروق وحده لا يستطيع فتح نافذة، ولذلك لا يستطيع على مسار EVM أن يتصرف إلا ضمن ما تسمح به نافذة مفتوحة أصلاً (فالنافذة لا تحدّ مقادير الرموز ولا الموافقات القائمة).

| الحد        | النطاق             | المعنى |
| ----------- | ------------------ | ------- |
| `blocks`    | 1 – 17,280         | المدة التي تبقى فيها النافذة مفتوحة، محسوبة بالكتل ابتداءً من الكتلة التي تفتحها |
| `max-txs`   | 1 – 1,000          | عدد معاملات EVM التي تقبلها |
| `max-value` | أكبر من 0، بوحدة `uqor` | إجمالي التدفق الخارج الذي تقبله: القيمة المحوَّلة **زائداً** أقصى رسوم قد تدفعها كل معاملة (حد الغاز × أقصى رسوم لكل وحدة غاز)، محوَّلاً إلى `uqor` ومقرَّباً إلى الأعلى |

أي حد ينفد أولاً يغلق النافذة. الحدود الثلاثة مطلوبة؛ وفتح نافذة جديدة يحل محل النافذة القائمة؛ والمعاملة التي تُقبل ثم تفشل تستهلك مع ذلك خانتها وميزانية قيمتها؛ ونشر العقود يُحتسب كأي معاملة أخرى. `blocks` عدد كتل وليس مدة زمنية: 17,280 كتلة تساوي نحو 15 ساعة على الشبكة الرئيسية (نحو 3.1 ثانية لكل كتلة) ونحو 6 ساعات على شبكة الاختبار (نحو 1.3 ثانية لكل كتلة في 27 أكتوبر 2026؛ ويتفاوت زمن الكتلة في شبكة الاختبار).

**حد القيمة يحتسب QOR الأصلي فقط.** فتحويل الرموز أو الموافقة (approval) أو أي استدعاء عقد آخر قيمته صفر، لذا لا يُحتسب من `max-value` (بل أقصى رسومه فقط). أما **نطاق** النافذة (الشبكة الرئيسية v3.2.3 وما بعده) فيضيّق المستلمين الذين تقبلهم، لكنه لا يحدّ مقادير الرموز:

| خيار النطاق (علامة CLI) | حقل الرسالة | ما تقبله النافذة |
| ----------------------- | ------------- | ---------------------- |
| `--native-only`         | `native_only` | تحويلات QOR الأصلي العادية فقط: بلا calldata، وبلا إنشاء عقود، وبلا مستلم يحمل شيفرة، وبلا تفويض EIP-7702 |
| `--allowed-targets 0xA,0xB` | `allowed_targets` | المعاملات التي يكون مستلمها أحد العناوين المدرجة (20 بايتاً) فقط؛ ويُرفض إنشاء العقود |

يحدّ `allowed_targets` من **أي** العقود والرموز يجوز للنافذة أن تلمسها، لا من **المقدار**. فالرمز المدرج يقبل أي مقدار منه، بما في ذلك `approve`، ويمكن للعقد المدرج أن ينقل كل ما تسمح به شيفرته وموافقاته القائمة، لذا لا تدرج عقود المُمرِّر أو الموجِّه العامة. وتحدّ النافذة معاملات مسار EVM فقط (الموقَّعة بتوقيع كلاسيكي). أما رسائل Cosmos الموقَّعة بتوقيع PQC الهجين فخارجها. وقبل v3.2.8 كان ذلك يشمل استدعاءات cross-VM وauthz؛ ومنذ v3.2.8 (على شبكة الاختبار فقط إلى حين ترقية لاحقة للشبكة الرئيسية) يستخدم استدعاء cross-VM إلى EVM وتحويل ERC-20 المرسلان بموجب منحة authz نافذةَ **المانح**، وتحتاج precompile الجسر `0x0901` إلى نافذة تدرجها.

النافذة المفتوحة بلا نطاق تتصرف تماماً كما كانت من قبل. وتُرفض المعاملة الخارجة عن النطاق بالرمز 27 (تقول الرسالة إن النافذة "does not admit this transaction"). ويُبلغ كل من `GET /qorechain/pqc/v1/evm_window/{address}` و`qorechaind query pqc evm-window` عن `native_only` و`allowed_targets`، ويحملهما الحدث `pqc_evm_window_opened` عند ضبطهما.

**الخطوات** (الشرح الكامل في [معاملتك الأولى](/getting-started/first-transaction#evm-window)):

1. سجّل مفتاح ML-DSA-87 الخاص بك مرة واحدة (`tx pqc register-key-v2` أو `register-key`، مع `--gas 600000 --fees 60000uqor`؛ هذه المعاملة الواحدة معفاة من شرط التوقيع الهجين، ولذلك يستطيع الحساب الجديد أن يبدأ). راجع [التوقيع ما بعد الكمومي](/developer-guide/post-quantum-signing#pqc-key-registration).
2. افتح نافذة. هي معاملة في مسار Cosmos، لذا أنتجها غير موقَّعة ووقّعها بالتوقيع المشترك بمفتاح ML-DSA الخاص بك (يقبل `max-value` الوحدة `uqor` أو `qor`؛ و`1000qor` تعني 1,000 QOR):

   ```bash
   qorechaind tx pqc open-evm-window 7200 20 1000qor --from mykey \
     --chain-id qorechain-vladi --gas 400000 --fees 40000uqor --generate-only > w.json
   qorechaind tx pqc cosign w.json --from mykey --pqc-key mypqc --chain-id qorechain-vladi

   # the same window narrowed to plain QOR transfers (mainnet v3.2.3 and later):
   qorechaind tx pqc open-evm-window 7200 20 1000qor --native-only --from mykey \
     --chain-id qorechain-vladi --gas 400000 --fees 40000uqor --generate-only > w.json
   ```

3. تحقق مما تبقّى: `qorechaind query pqc evm-window <address>` أو `GET /qorechain/pqc/v1/evm_window/{address}` (يجيب بـ `found: false` عند عدم وجود نافذة).
4. أرسل معاملات EVM كالمعتاد. فتح النافذة معاملة في مسار Cosmos وتزيد رقم تسلسل الحساب، وهو أيضاً nonce الخاص بـ EVM، ولذلك اقرأ الـ nonce **بعد** فتح النافذة ثم وقّع.

### خيارات النافذة المضافة في v3.2.8 {#evm-window-v328}

منذ الإصدار v3.2.8 (على شبكة الاختبار فقط إلى حين ترقية لاحقة للشبكة الرئيسية) تحمل `MsgOpenEVMWindow` ثلاث قوائم اختيارية، في كل منها 16 عنصراً على الأكثر. والنافذة التي لا تحملها تتصرف كما كانت، باستثناء قاعدة الرفض الافتراضي أدناه.

| حقل الرسالة | علم CLI | ما يسمّيه |
| ----------- | ------- | --------- |
| `validators` (7) | `--validators` | العقود التي يُحتسب فحصها لتوقيع الحساب لأفعاله: وحدة تحقق تستدعيها عقد محفظة، أو نقطة دخول ERC-4337 |
| `staking_validators` (8) | `--staking-validators` | عناوين مشغّلي المدققين (`qorvaloper…`) التي يجوز للحساب التفويض أو إعادة التفويض إليها عبر النافذة |
| `ibc_receivers` (9) | `--ibc-receivers` | أزواج `<channel>/<receiver>` الدقيقة التي يجوز أن يذهب إليها تحويل IBC من QOR الأصلية؛ تُقارن القناة والمستلم بايتاً ببايت (`channel-0`، مستلم bech32 بأحرف صغيرة) |

**الـ precompiles القياسية مرفوضة افتراضياً.** بالنسبة لحساب تفوّضه نافذة، تُرفض أي طريقة في precompile قياسية (التخزين staking والتوزيع distribution وICS-20 والحوكمة gov والمعاقبة slashing وprecompiles رموز ERC-20) ما لم تكن في الجدول أدناه وتدرج النافذة الـ precompile في `allowed_targets`.

| الـ precompile | الطريقة | تُقبل عندما |
| -------------- | ------- | ----------- |
| distribution | `claimRewards`، `withdrawDelegatorRewards` | تُدفع المكافآت إلى الحساب نفسه |
| distribution | `withdrawValidatorCommission` | يكون المدقق هو مدقق الحساب نفسه ويدفع إلى الحساب نفسه |
| distribution | `depositValidatorRewardsPool` | يكون المدقق في `staking_validators` وتكون كل العملات QOR الأصلية |
| staking | `delegate`، `redelegate` | يكون المدقق الوجهة في `staking_validators` |
| ICS-20 | `transfer` | QOR أصلية، عبر المنفذ `transfer`، دون memo، إلى زوج في `ibc_receivers` |
| precompiles رموز ERC-20 | `transfer`، `transferFrom`، `approve` | QOR أصلية؛ ورمز آخر فقط عندما تدرج النافذة عنوان ذلك الرمز |

إن precompile التخزين (`0x…0800`) وprecompile التوزيع (`0x…0801`)، شأنهما شأن بقية الـ precompiles القياسية في هذا الجدول، **غير مفعّلة حاليًا على شبكة الاختبار ولا على الشبكة الرئيسية**؛ ويمكن للحوكمة تفعيلها. والاستدعاء الموجَّه إلى عنوان precompile غير مفعّل يصل إلى عنوان لا يحوي شيفرة: ينجح ولا يفعل شيئًا ويستهلك الغاز مع ذلك. وتنطبق حقول النافذة `staking_validators` و`validators` و`ibc_receivers` متى فُعّل precompile. وللتخزين (staking) والمطالبة بالمكافآت، استخدم رسائل Cosmos الأصلية (QoreX، أو أوامر qorechaind الخاصة بالتخزين والتوزيع). وحين يكون precompile مفعّلًا تكون مقاديره بوحدة `uqor` (6 منازل عشرية) لا بوحدات EVM ذات 18 منزلة عشرية.

كل ما عدا ذلك يُرفض عبر النافذة: إلغاء التفويض والتصويت وغيره من إجراءات الحوكمة وتغيير عنوان السحب وإنشاء مدقق أو تعديله وتمويل مجمع المجتمع. أرسلها كمعاملات Cosmos موقَّعة بتوقيع ما بعد الكم.

**التواقيع المفحوصة على السلسلة تحتاج العقد المتحقق داخل النافذة.** يفحص عقد توقيعَ EIP-2612 permit أو تحويل Permit2 أو أمر EIP-712 أو المعاملة الوصفية (meta-transaction) باستخدام `ecrecover`. منذ v3.2.8 (على الشبكتين، متى طبّقته الشبكة) ينجح هذا الفحص لحساب يملك مفتاح ما بعد الكم صالحاً للاستخدام فقط ما دامت نافذة الحساب نفسه الحية تقبل العقد المتحقق، وهو الرمز نفسه أو Permit2 نفسه، لا الموجِّه الذي يمرّر الاستدعاء. أدرجه في `allowed_targets` وافتح النافذة **قبل** أن يوقّع المستخدم. وبدون تلك النافذة يُعامل التوقيع كأنه غير صالح ويرفضه العقد. والـ permit أو الموافقة الممنوحة داخل نافذة تبقى بعد إغلاقها، فراجع الموافقات وألغِها عند انتهاء الجلسة.

**تغيير المفاتيح يغلق النافذة.** تدوير مفتاح ما بعد الكم للحساب أو ترحيله أو إعادة تسجيله يحذف نافذته المفتوحة وموافقة EIP-7702 الخاصة به؛ افتح النافذة من جديد بعد ذلك. ويجب أن تكون رسائل النافذة والموافقة رسالة الحساب نفسه من المستوى الأعلى وموقَّعة بتوقيع ما بعد الكم: ولا يمكن إرسالها عبر authz ولا منحها لحساب آخر.

أغلق النافذة مبكراً باستخدام `qorechaind tx pqc close-evm-window` (بنمط `--generate-only` و`cosign` نفسه)، مثلاً إذا اشتبهت في انكشاف المفتاح الكلاسيكي: وكل ما كانت النافذة ما زالت تقبله يُرفض ابتداءً من الكتلة التالية.

### تفويضات EIP-7702 {#eip-7702}

لا يسري تفويض EIP-7702 لحسابك (معاملة من النوع 4) إلا بموافقة حسابك نفسه بمفتاح ما بعد الكم، منذ v3.2.2. سجّل الموافقة أولاً بالرسالة الموقَّعة هجيناً في مسار Cosmos `MsgAuthorizeEVMDelegation` (`qorechaind tx pqc authorize-evm-delegation <delegate_0x> <blocks>`)؛ وهي لمرة واحدة، وتنتهي بعد العدد المحدد من الكتل، ويُلغيها `close-evm-window`. والقيمة التي تغادر حساباً مفوَّضاً تُحتسب على نافذة **ذلك** الحساب نفسه، والمعاملة الفاشلة من النوع 4 تحتفظ بالتفويضات التي طبّقتها، ويزيل `qorechaind tx pqc clear-evm-delegation` أي تفويض. ويجيب التفويض المرفوض بالرموز من 60 إلى 63. اقرأ الموافقة عبر `GET /qorechain/pqc/v1/evm_delegation_consent/{address}`.

| الرفض (النطاق `pqc`) | المعنى |
| ------------------------- | ------- |
| الرمز 26 | لا توجد نافذة مفتوحة للمرسل، أو أن المرسل ليس لديه مفتاح PQC مسجَّل |
| الرمز 27 | النافذة منتهية الصلاحية أو مستنفدة (تُظهر الرسالة أي حد استُنفد)، أو أن المعاملة خارج نطاق النافذة |
| الرمز 28 | حدود نافذة غير صالحة عند فتحها، أو لا يوجد مفتاح مسجَّل عند تلك النقطة |

مع SDK لغة TypeScript (الإصدار 0.8.2 وما بعده): `openEvmWindowMsg` و`closeEvmWindowMsg` و`fetchEvmWindow({ rest, address })` و`classifyEvmWindowRejection(err)` (`"no-pqc-key" | "no-window" | "exhausted" | "invalid"`). يضيف SDK 0.9.0 وما بعده (والإصدار 0.13.0 هو الحالي) خيارات النطاق (`nativeOnly` و`allowedTargets`) إلى `openEvmWindowMsg` وبُناة موافقة EIP-7702 (`authorizeEvmDelegationMsg` و`clearEvmDelegationMsg` و`fetchEvmDelegationConsent`)؛ أما الإصدارات السابقة لـ 0.9.0 فتبني النافذة غير المقيّدة بنطاق فقط، لذا استخدم `qorechaind` لبقية ذلك (انظر [دليل EVM في SDK](/sdk/guides/evm#evm-window-scope)).

## مساحة `qor_` المخصّصة {#custom-qor_-namespace}

توسّع QoreChain واجهة JSON-RPC بمساحة `qor_` للاستعلامات الخاصة بالسلسلة. الطرق الواردة أدناه مخطَّط لها:

:::warning غير مخدَّمة بعد
الطرق الواردة في الجدول أدناه مخطَّط لها وغير مخدَّمة: تُرجع كل منها `-32601` (الطريقة غير موجودة). والطريقة الوحيدة المخدَّمة من هذه المساحة هي `qor_getKEMKey`، ولا تُخدَّم إلا حيث تسرد العقدة `qor` ضمن مساحات أسمائها: فحسب ما لوحظ في 7 نوفمبر 2026، تسرد شبكة الاختبار `qor` وتردّ عليها، بينما لا تسرد نقطة نهاية الشبكة الرئيسية العامة سوى `eth` و`net` و`rpc` و`txpool` و`web3` وتردّ بالرمز `-32601`. راجع [مساحة `qor_`](/api-reference/json-rpc-qor_-namespace) لمعرفة الحالة وبدائل REST (مثلاً `GET /qorechain/pqc/v1/account/{address}` لحالة مفتاح PQC).
:::

| الطريقة                      | الوصف                                                              |
| ----------------------------- | ------------------------------------------------------------------- |
| `qor_getPQCKeyStatus`         | التحقق مما إذا كان الحساب يمتلك مفتاح PQC عامًا مسجّلًا             |
| إحصاءات الذكاء الاصطناعي (مخطَّطة) | استرجاع إحصاءات محرك الذكاء الاصطناعي (عدد الحالات الشاذة، توزيع المخاطر)؛ اسم الطريقة غير نهائي |
| `qor_getCrossVMMessage`       | الاستعلام عن حالة رسالة عبر الآلات الافتراضية (Cross-VM) عبر المعرّف |
| `qor_getPoolClassification`   | الحصول على تصنيف تجمّع المدقّقين (RPoS/DPoS/PoS)                     |
| `qor_getReputationScore`      | الاستعلام عن درجة سمعة أحد المدقّقين                                 |
| `qor_getAbstractAccount`      | استرجاع إعدادات الحساب المجرّد                                       |

مثال باستخدام `curl`:

```bash
curl -X POST http://localhost:8545 \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "method": "qor_getPQCKeyStatus",
    "params": ["0xYourAddress"],
    "id": 1
  }'
```
